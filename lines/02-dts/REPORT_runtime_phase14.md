# REPORT R14 — два локальні static data-flow трейси (R14, STATIC ONLY)

**Режим:** static only, без ADB/device/PM/DM/runtime/patch — за вказівкою.
**Вхід:** R13 (constructor `0x045d4c/8a/ca`, формат licensee `0x02813ae2`).
**Образ:** `r8_out/mst_codec_r2_MS12V22.bin` (DEC, = `aucode_adec_r2_MS12V22.bin`).

---

## 0. Підсумок

| п. | задача | результат |
|---|---|---|
| A | `r3` у constructor-і | **ВСТАНОВЛЕНО**: caller-supplied pointer; абсолютної адреси немає |
| B | 4 джерела `*_licensee` | **НЕ ВСТАНОВЛЕНО**; R13-адресу `0x00010A76` **відкликано** |
| 3 | вікно `0x0001xxxx` | **НЕ ДОВЕДЕНО**; передумова знята разом із п.B |
| 4 | семантика op-кодів | таблиця з крос-чеками; **op 0x32 і op 0x3b — проблематичні** |
| 5 | `output_spdifSz` | без змін: посилань не знайдено, **не proven** |
| 6 | gate `Invalid Spdif license` | не реконструював (mixed-width), як і дозволено |

**Найважливіше методологічне:** доведено, що **статистичні** підрахунки `movhi` у цьому
образі — шум (15078 знахідок проти 15470 очікуваних випадково). Надійно валідовані
лише **два** вікна адрес: `0x0281xxxx` (rodata) і `0x1c01xxxx` (DM). Усе інше потребує
семантичної перевірки, а не частоти.

## A. IEC61937 constructor → `r3`

### A.1 Що лишається чинним з R13 (PROVEN)

```
0x045d4c / 0x045d8a / 0x045dca   (три копії блоку, фази 0 → 2 → 2)

  [r3+0x16d] <- Pa  (0xF872, з immediates 0x024c0c / 0x02abac / 0x02b5fc / 0x045da0)
  [r3+0x16f] <- Pb  (0x4E1F, з immediates 0x045d50 / 0x045d8e / 0x045dce / 0x1c1270)
  [r3+0x171] <- data-type
  [r3+0x173] <- length
```
Чотири 16-бітні поля з кроком 2 — точна структура IEC61937-пreamble, і вона збігається
з runtime-вмістом DM `0x0A00–0x0A03` = `f872 4e1f 0001 3000`.

### A.2 Що нового в R14: `r3` не має абсолютної адреси

Перевірено три способами:

1. **У всьому діапазоні `0x043000–0x04a000` немає жодної пари `movhi 0x1c01 + ori`.**
   Повний валідований набір абсолютних DM-звернень DEC: `0x1ad0, 0x1000, 0x1e10, 0x1080,
   0x1bc8, 0x26b0, 0x5840, 0x1a90, 0x2678, 0x2594, 0x259c, 0x2000, 0xd0e7`.
   ⇒ constructor **не звертається до DM-вікна абсолютно**.
2. **У 352 байтах безпосередньо перед constructor-ом (`0x045c00–0x045d60`) — нуль
   інструкцій, що пишуть `r3`.**
3. У ширшому вікні `0x045800–0x045d60` — лише **дві**, і жодна не є свіжим `movhi`:
   ```
   0x045990  fc6b57bd  ori  r3, r11, 0x57bd
   0x045aae  c8600400  op32 r3, r0 , 0x0400
   ```
   Обидві зберігають старші біти іншого регістра, тобто не матеріалізують нову адресу.

### A.3 Висновок A (PROVEN / INFERENCE)

> **PROVEN:** `r3` не обчислюється як абсолютна адреса ні в самому блоці, ні в
> найближчих ~1.4 КБ. Адресація вихідного буфера — **динамічна, через базовий регістр**.
>
> **INFERENCE (висока):** `r3` — **вказівник, отриманий від caller-а** (аргумент функції
> або global/descriptor pointer, що живе між викликами). Preamble лежить у структурі
> за цим вказівником зі зміщенням **`+0x16d … +0x173`**.
>
> **НЕ ВСТАНОВЛЕНО:** абсолютна адреса дескриптора; який саме буфер (SPDIF чи HDMI —
> у DEC є `Mstar_DTS_Hdmi_Packer`); чи збігається він із runtime DM `0x0A00`.

```
constructor
   ↓
r3  ← caller argument / descriptor pointer   (не абсолютна адреса)
   ↓
output structure: preamble @ r3 + 0x16d/16f/171/173
```

### A.4 Супутня знахідка: `r11` = DM `0x1BC8`

Валідовані `movhi+ori` пари з `rD == 11`:

| адреса | скільки |
|---|---|
| **`0x1c011bc8` (DM 0x1BC8)** | **6** |
| `0x08c15840` | 4 |
| інші (`0xc77e7064`, `0x02a1ed48`, …) | по 1–2 |

Тобто **`r11` найчастіше тримає `0x1c011bc8`** — вказівник на структуру в DM `0x1BC8`
(цей самий `0x1bc8` входить до топ-списку абсолютних DM-звернень). Оскільки аргументи
принта зберігаються як `sw 0x172(r11), rX`, блок аргументів лежить у **DM `0x1BC8 + 0x172`**.

Гіпотеза для перевірки (НЕ доведена): `ori r3, r11, 0x57bd` @ `0x045990` може бути
тим самим механізмом (похідний від `r11` вказівник), але `ori` — побітова операція, тому
пряме додавання не випливає. Перевірити пізніше.

## B. `dts_licensee` — 0x01e64a–0x01e686

### B.1 Що підтверджено

```
0x01e66c  c0600281  movhi r3, r0, 0x0281      (фаза 0)
   ... 14 байт, між ними щонайменше одна 16-бітна інструкція ...
0x01e67a  fc633ae2  ori   r3, r3, 0x3ae2      (фаза 2)
                    -> 0x02813ae2 = "dts_licensee=%d, lbr_licensee=%d,
                                     xll_licensee=%d, transcoder_licensee=%d"
0x01e65a  d46b0172  op35  r3, r11, 0x0172     sw 0x172(r11), r3
```

* Формат — **PROVEN** (резолвиться в реальний рядок).
* Механізм передачі аргументів через блок у пам'яті за `r11` — **PROVEN**.
* Зсув фази 0 → 2 між `movhi` та `ori` = **підтверджена змішана ширина** в цьому вікні.

### B.2 Що ВІДКЛИКАЄТЬСЯ з R13

R13 стверджував:
```
movhi r23,0x0001 -> op32 r23,r23,0x0870 -> r23 = 0x00010870 -> load [0x00010A76]
```

**Крос-чек (вимога п.4) не пройдений.** Якби `op 0x32` справді був `ori`-подібним
формувачем адреси, то десь мали б існувати пари
`movhi rX, 0x0281` + `op32 rX, rX, <lo>` з резолвленням у рядок. Перевірено по всьому
образу: **0 таких сайтів** (при тому, що звичайних `movhi 0x0281 + ori(0x3f)` — 369).

Наслідки:
* `r23 = 0x00010870` — **НЕ ПІДТВЕРДЖЕНО**;
* `r4 ← [0x00010A76]` — **НЕ ПІДТВЕРДЖЕНО**;
* твердження «4 licensee лежать поруч у вікні `0x0001xxxx`» — **ЗНЯТО**.

Заувага про raw-байт у вікні: послідовність `83 46 / 83 28 / 83 0a / 82 ec`
(`0x01e646–0x01e64f`) спадає на 0x1e — це або таблиця, або 16-бітні інструкції;
без семантики op-кодів розрізнити неможливо.

### B.3 Висновок B

```
dts_licensee        ← НЕ ВСТАНОВЛЕНО
lbr_licensee        ← НЕ ВСТАНОВЛЕНО
xll_licensee        ← НЕ ВСТАНОВЛЕНО
transcoder_licensee ← НЕ ВСТАНОВЛЕНО
```

Відомо лише: значення **не є константами в сайті принта** (немає immediates),
а надходять у принт через **блок аргументів у пам'яті за `r11`** (`sw 0x172(r11), r3`
для покажчика формату; аналогічно для решти). Точні адреси/зсуви потребують семантики
op `0x32`, `0x03`, `0x05`, `0x20`, `0x23`.

## 3. Вікно `0x0001xxxx`

**Статус: НЕ ДОВЕДЕНО (і наразі безпредметно).**

* Передумова (`0x00010A76` як адреса licensee) знята у §B.2.
* Прямої вказівки з loader-а на вікно `0x0001xxxx` немає: відомо лише, що DEC-образ
  копіюється в `MAD(2)+0`, а DM-звернення йдуть через `0x1c01xxxx`.
* Гістограма `movhi`-вікон **статистично порожня** (див. §0): пошук на кожному зсуві
  дає 15078 знахідок проти 15470 очікуваних випадково, тобто ~97 % — шум. Тому
  «частота» не може бути доказом існування вікна.

**Валідовані вікна адрес (тільки ці два):**

| hi16 | простір | як валідовано |
|---|---|---|
| `0x0281` | rodata | `movhi+ori` резолвляться у реальні рядки (369 сайтів) |
| `0x1c01` | DM (`N ↔ 0x1c010000+N`) | резолвляться у ~13 повторюваних DM-адрес, включно з `0x1c011000` з R10 |

Решта кандидатів (`0x0107`, `0x040f`, `0x020f`, `0x0301`, …) — за рівнем хибних спрацьовувань.

## 4. Семантика op-кодів (з крос-чеками)

| op | припущення | крос-чек | вердикт |
|---|---|---|---|
| `0x30` | `movhi rD, imm16<<16` | `0x0281`→рядки, `0x1c01`→DM | **ВАЛІДОВАНО** |
| `0x3f` | `ori rD, rA, imm16` | ті самі 369 + 118 сайтів | **ВАЛІДОВАНО** |
| `0x39` | `call` | трапляється після формування формату принта | **СЛАБКО** |
| `0x35` | `sw imm16(rA), rB` | один зв'язний сайт `0x01e65a` (`sw 0x172(r11), r3`) | **SUPPORTED, незалежно не підтверджено** |
| `0x3b` | ld/st | **СУПЕРЕЧНІСТЬ** (див. нижче) | **НАПРЯМ НЕ ВИЗНАЧЕНИЙ** |
| `0x32` | (припускалось `ori`) | 0 сайтів `movhi 0x0281 + op32` | **НЕ ПІДТВЕРДЖЕНО** |
| `0x03`, `0x05`, `0x20`, `0x23` | невідомо | — | **НЕВІДОМО** |

### Суперечність op `0x3b`

* У блоці constructor-а (`0x045d8a` тощо) `op 0x3b` **мусить бути store**: інакше
  `ori r24, r0, 0x4e1f` стає мертвим кодом, а Pb нікуди не пишеться.
* У `0x01e5ea` (`ec8a0cf6`, відразу після `movhi r10,0x1c01 / ori r10,r10,0x1000`,
  перед принтом `Mstar_DTS_Hdmi_Packer error=%x`) `op 0x3b` **виглядає як load**:
  інакше принт не має аргументів.

Порівняння кодів слів не виявило біта напрямку в межах відомого поля формату.
**Висновок:** напрям `op 0x3b` не визначається з 32-бітного підмножини. Це прямо
обмежує і трактування блоку constructor-а: інтерпретація «store» обрана як єдина
зв'язна, але вона **не є незалежно підтвердженою**.

## 5. `output_spdifSz`

Без змін проти R13, і за вказівкою — **не називається proven**.

* Рядок `Invalid Spdif license:%d, output_spdifSz:%d` → VA `0x02811904`.
* `ori rN,rN,0x1904` — 2 входження, обидва в даних; слова `0x02811904` в образі немає.
* Отже статично: **ні адреси, ні значення, ні readers/writers не знайдено.**
* Єдине, що можна сказати: змінна друкується **в тому самому принті**, що й значення
  ліцензії, тобто формально належить до того ж output-шляху, — але це властивість
  рядка, а не доказ участі в умові.

---

## 6. Gate `Invalid Spdif license`

Не реконструювався. Сайт принта не локалізований (§5), а кільцеві 16/32-бітні переходи
не дають надійного control flow. За вказівкою — ніякої спекулятивної реконструкції
гілок.

Якщо з'являться data-flow якорі, порядок буде:
```
license state -> output decision -> IEC61937 constructor
```
Наразі ланок між ними **немає**.

## 7. Зведені трейси R14

### A — IEC61937 (завершено настільки, наскільки дозволяє static)
```
Pa  <- ori rX, r0, 0xf872    (0x024c0c / 0x02abac / 0x02b5fc / 0x045da0)
Pb  <- ori rX, r0, 0x4e1f    (0x045d50 / 0x045d8e / 0x045dce / 0x1c1270)
type/len                     (r23, r5)
        ↓
[r3 + 0x16d/0x16f/0x171/0x173]
        ↓
r3 = caller-supplied descriptor pointer   (НЕ абсолютна адреса; DM-вікно не використовується)
```

### B — DTS license (НЕ завершено)
```
dts_licensee        \
lbr_licensee         \  джерела НЕ встановлені; R13-адресу 0x00010A76 відкликано
xll_licensee         /  відомо лише: передача через arg-блок за r11
transcoder_licensee /
        ↓
print (формат 0x02813ae2, покажчик формату -> sw 0x172(r11), r3)
```

### Static hypothesis (чітко inference, не proven)
```
license state (невідома адреса)
        ↓  ???

        ↓  ???
IEC61937 constructor (0x045d4c/8a/ca)
```
**Жодна з трьох стрілок не доведена.**

## 8. Що блокує і що робити далі

1. **Семантика `op 0x32` і `op 0x03/0x05`** — без них трейс B не закривається.
   Мінімальний незалежний тест: знайти будь-який `movhi` з **відомим** hi16
   (`0x0281` або `0x1c01`), за яким іде `op32`/`op03` з тим самим `rD`, і перевірити,
   чи резолвиться результат у рядок/DM-адресу.
2. **Напрям `op 0x3b`** — вирішується так само: знайти `op 0x3b` безпосередньо після
   завантаження immediate (тоді це store) або безпосередньо перед використанням `rD`
   (тоді це load) у двох незалежних місцях.
3. **`r3`**: шукати найближчий `call` перед `0x045800` і трейсити від нього; або
   знайти всі `movhi+ori`, що формують `0x1c011bc8`, і перевірити, чи не є
   `r3` похідним від того самого дескриптора.
4. Коли з'явиться ADB — перевірити конкретно: DM `0x1BC8+0x172` (arg-блок),
   DM `0x1BC8`, DM `0x0A00` (preamble), DM `0x1000` (база стану з R10/R12).
