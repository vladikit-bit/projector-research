## 1. T615 / MT9615 / MT5889 — verdict: USEFUL BUT PARTIALLY COMPARABLE
- SoC: MT9615 = MT5889 alias (XDA/community consensus + displayspecifications `MT9615/MT5889`; 4xA73 + G52MP2, 28nm; 1.3 vs 1.6GHz binning). Do NOT confuse with Unisoc Tiger T615. T615 itself = TCL chassis/platform, not a chip (T615T01..T03).
- BSP match is unusually exact: early T615 (C728/C825, 2021) = Android 11 TV + kernel 4.19.116+ + build AR2101 — same generation as TD98 Pro (Android 11 SDK30 + 4.19.116). Later T615 keep Android 11/AR2101 through 2023-2024 OTAs.
- Shared lineage: MediaTek absorbed MStar TV group (2019); MStar IP (incl. interrupt controller) reused in MTK TV SoCs; MBoot/Supernova/vendor BSP philosophy common. BUT no public evidence that T615 firmware contains MI_AUDIO/UtopiaIoctl/utpa2k/mik-style stack (no published teardown of V8-T615T03 zips at that depth).
- Vendor stack differs: TCL = Google TV + TCL UI + Dolby MS12Z + Onkyo + eARC-centric + ProjectID whitelist; TD98 = projector ODM + SPDIF/optical + MStar Utopia/MI without MS12. Physical outputs differ (eARC/ARC cases vs SPDIF).
- Phenomenology converges STRONGLY and usefully: DTS availability varies by firmware on identical silicon (4PDA FAQ: DTS 5.1↔3.1↔stereo↔hoarseness across V272/V477/V481/V488; XDA hunting old V8-T615T01-LF1R074 as "working"; C8K V590 fixed HDMI-in but broke internal apps); Auto vs Pass Through; ARC-stereo vs optical-5.1; native-OK vs Kodi-fail; DTS reserved to vendor player via private pipeline (Nova dev quote). This is direct evidence that codec availability is vendor-software-determined, not SoC capability — supporting our software-block model without proving any TD98 mechanism.
- Firmware depth exists: T615T03 V407 IMG → V440 IMG → OTAs V462→V474→V503→V558→V562→V590→V614+ (plus T615T01 ATV branch, T615T02 NA). IMG (full, destructive) vs OTA (incremental; late V6xx OTAs leave kernel/system — "fake update"). Hunting multiple generations of ONE model (e.g. C825/C835 V407→V440→V462…V590) is SENSIBLE: cheapest web-side way to localize the layer (policy/HAL/MS12/kernel) where passthrough regressed.
- Verdict: NOT a donor for porting (ProjectID/brick, panel/tuner/license differences), but a WORKING HYPOTHESIS REFERENCE: where to look (policy vs private pipeline, MS12 vs DTS-HD, IEC RAW vs IEC, EDID/192kHz detection) + proof that "SoC supports DTS" means nothing without vendor code.
- Source quality: community consensus + OTA metadata fingerprints (medium-high for procedure/history); spec aggregators (medium); NO MediaTek datasheet, NO T615 audio-HAL teardown (explicit gap).

## 5. Method notes for the next model
- Ghidra script provider poisons after several runs (OSGi bundle error even for proven scripts); mitigation: fresh filename + fresh -scriptPath dir per run; Java API only (PyGhidra unavailable headless here); Disassembler via ghidra.app.cmd.disassemble.DisassembleCommand (not ghidra.app.util).
- ET_REL imports remap addresses: never assume section-relative VAs in Ghidra; validate via raw WORD reads against file offsets first.
- PowerShell: avoid long inline python -c (quoting loss); file scripts only; no `head` (use Select-Object).
- mik.ko .text ends 0x2CA2D8 — any address above is suspect; utpa2k.ko .text ends 0x6287DC.
- Jump-table bases: always apply pc+8 explicitly and anchor on adjacent opcode words (E28F1000/E791F100 pattern).
- Parser regexes must accept operand-less instructions (`bt.inst16_4 | 8595`).
