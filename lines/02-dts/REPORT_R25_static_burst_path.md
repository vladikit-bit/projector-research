## 2. IEC61937 construction — PROVEN (частково)

```
0x01BEF6: FF20F872   ori  r25, r0, 0xF872     -> r25 = Pa
0x01BEFA: EF2A250D   0x3B r25 <-> [r10+0x250D]      (запис Pa)
0x01BEFE: EF0A00A2   0x3B r24 <-> [r10+0x00A2]
0x01BF02: FF204E1F   ori  r25, r0, 0x4E1F     -> r25 = Pb
0x01BF06: EF2A250F   0x3B r25 <-> [r10+0x250F]      (запис Pb)
...
0x01C052: EF2A2511   0x3B r25 <-> [r10+0x2511]      (позиція Pc)   [фаза 2 — валідна]
0x01C056: EF0A2513   0x3B r24 <-> [r10+0x2513]      (позиція Pd)   [фаза 2 — валідна]
0x01BF3C: EAEA2515   0x3A r23  <-> [r10+0x2515]
```

**Кроки `0x250D → 0x250F → 0x2511 → 0x2513` = по 2 байти** — чотири послідовні 16-бітні halfword.
Це точно компонування преамбули IEC61937: **Pa, Pb, Pc, Pd**.

Інші сайти констант:

| Константа | Адреса | Інструкція | Регістр |
|---|---|---|---|
| Pa `0xF872` | `0x01BEF6` | `ori r25, r0, 0xF872` | r25 |
| Pa `0xF872` | `0x01EDA6` | `ori r25, r0, 0xF872` | r25 (другий сайт) |
| Pb `0x4E1F` | `0x01BF02` | `ori r25, r0, 0x4E1F` | r25 |
| Pb `0x4E1F` | `0x01B4B0` | `ori r23, r0, 0x4E1F` | r23 |
| Pb `0x4E1F` | `0x01F8AA` | `ori r23, r0, 0x4E1F` | r23 |

Усі — «чисті» негайні (`rA = r0`), тобто це справжня матеріалізація констант, а не випадковий збіг у даних.

## 3. Data-type selection — НЕ ПІДТВЕРДЖЕНО (корекція R22)

R22 стверджував: «data-type table ~`0x13f181`, DTS=`0x0B`, AC3=`0x01`».

**Перевірка спростовує це.** Область `0x13f100–0x13f240` — це **монотонно спадний ramp** 32-бітних BE значень (групи по 3–4):

```
0x16, 0x15, 0x14, 0x13, 0x12, 0x11, 0x10, 0x0F, 0x0E, 0x0D, 0x0C, 0x0B, 0x0A, 0x09, 0x08, 0x07, 0x06, 0x05, 0x04
```

- Значення `0x0B` присутнє, але воно **лише один крок спадної послідовності** (поряд `0x0C`, `0x0D`, `0x0A`, `0x09`).
- Значення **`0x01` (AC3) відсутнє** взагалі (найменше — `0x04`).
- Отже це не таблиця відповідності «кодек → IEC data-type», а ймовірно таблиця розмірів/лічильників.

**Статус:** твердження R22 про data-type table — **НЕ ПІДТВЕРДЖЕНО / спростовано**.
Позиція Pc (`[r10+0x2511]`) існує й записується, але її джерело в протрасованому вікні не встановлено.

## 4. Output destination

### PROVEN (структурно-відносне призначення)

Безперервний halfword-блок у структурі, на яку вказує **r10**:

```
[r10+0x250D] = Pa
[r10+0x250F] = Pb
[r10+0x2511] = Pc (позиція)
[r10+0x2513] = Pd (позиція)
[r10+0x2515] = далі (op 0x3A)
```

Інші поля тієї ж структури (для контексту): `+0x00A2`, `+0x24A2`, `+0x24D0`, `+0x24D4`, `+0x24DC`,
`+0x24E8`, `+0x24F0`, `+0x24F4`, `+0x24F8`, `+0x2500`, `+0x2504`, `+0x2508`.

### UNRESOLVED (абсолютна адреса)

- Базовий регістр **r10 не матеріалізується** через `movhi/ori` у діапазоні `0x01B000–0x01BF00`
  (пошук по всьому образу: `movhi r10` зустрічається 567 разів, але це інший, низькоадресний патерн
  `C15C0EE1`, не пов'язаний із цією функцією).
- Тому **абсолютна адреса призначення не встановлена**.

### Confidence

| Елемент | Confidence | Підстава |
|---|---|---|
| Матеріалізація Pa/Pb | **HIGH** | валідована `ori rD,r0,imm`; константи точно IEC61937 |
| Запис у `[r10+0x250D/0x250F]` | **MEDIUM-HIGH** | безпосередньо після завантаження константи в r25; op `0x3b` з rD=r25 |
| Напрямок (ST, а не LD) | **MEDIUM** | виводиться з data-flow; ISA-модель підтверджувала лише LD (R8) |
| Позиції Pc/Pd | **MEDIUM** | валідна фаза, крок 2, але значення не встановлені |
| Абсолютна база r10 | **UNRESOLVED** | не матеріалізується у tracing-вікні |

## 5. AC3 vs DTS static divergence

**Статичної розбіжності НЕ знайдено — і це очікувано.**

- `Pa = 0xF872` і `Pb = 0x4E1F` — **кодек-незалежні константи** стандарту IEC61937; вони однакові для AC3 і DTS.
- Розбіжність може бути лише в **Pc** (data-type: DTS `0x0B` / AC3 `0x01`) або в тому, **чи записується/емітується блок узагалі**.
- Жодне з цих двох статично не доведено.

Тобто сама конструкція преамбули — спільна; розбіжність (якщо є) лежить **праворуч** від неї: у виборі Pc або в емісії/передачі блоку.

## 6. Статуси

**VERIFIED (static, binary)**
- `"Packer"` / `"IEC"` / `DTSSPDIFPackFrame` — assert-рядки, не код.
- Pa `0xF872` і Pb `0x4E1F` матеріалізуються реальними інструкціями (`ori rX,r0,imm`) за адресами `0x01BEF6`, `0x01BF02` (+ інші сайти).
- Записи в `[r10+0x250D]` і `[r10+0x250F]` розташовані з кроком 2 байти — компонування Pa/Pb/Pc/Pd.
- Таблиця за `0x13f181` є спадною числовою послідовністю, а не таблицею типів кодеку.

**UNRESOLVED**
- Значення та джерело **Pc** (data-type) — не встановлено.
- Абсолютна адреса буфера призначення (база **r10**) — не встановлено.
- Чи виконується цей шлях для DTS; чи відрізняється Pc для AC3 і DTS.

**REFUTED**
- R22 «data-type table `0x13f181` з DTS=`0x0B` / AC3=`0x01`» — не підтверджено.
- SDO-імена як точки входу коду — спростовано (рядки).

# R25-B — static data-flow: producers of the 3rd/4th fields, consumer, buffer vs TX

**Режим:** тільки workspace, без device-дій. ISA-модель та ж (валідована).

## B.0 Валідація семантики `op 0x32`

Гістограма immediates для `op 0x32` з `rA = 0` (весь образ):

| imm | count | інтерпретація |
|---|---|---|
| `0x0800` | 284 | size/control |
| `0x0100` | 129 | |
| `0x0400` | 120 | |
| `0x8000` | 96 | |
| **`0xBB80`** | **61** | **= 48000 (sample rate)** |
| `0xFFFF` | 39 | маска |
| `0x0200` | 37 | |
| `0x5001` | 35 | |
| **`0xAC44`** | **35** | **= 44100 (sample rate)** |
| `0x0700/0x0900/0x0600` | 24/20/19 | |

Наявність `48000` і `44100` підтверджує: **`op 0x32` = завантаження 16-бітного immediate**.
Важливо: `op 0x32` **ніколи** не переносить `0x000B`, `0x0001`, `0x0015` (по 0 входжень).

## B.1 Producer 3-го поля `[r10+0x2511]`

```
0x01C042: EF0B8592  0x3B  r24 <-> [r11+0x8592]        (читання з іншої структури)
0x01C046: CB201800  op0x32 r25 = 0x1800               (immediate)
0x01C04A: 4F18180F  op0x13 r24 = f(r24, 0x180F)
0x01C04E: 2C009B21  op0x0B rD=0                        (без призначення)
0x01C052: EF2A2511  0x3B  r25 -> [r10+0x2511]   ***
```

- **Джерело r25: константа `0x1800`** (не таблиця, не codec ID, не повернення функції).
- `0x1800 = 6144` — не схоже на IEC61937 data-type (`0x0B` DTS / `0x01` AC3).
- Отже **позначення `+0x2511 = Pc (data-type)` НЕ підтверджено** і, судячи зі значення, ймовірно хибне.
- Кореляція: те саме значення `0x1800` завантажується в `r5` на `0x01C05A`, безпосередньо перед CALL — тобто `0x1800` схоже на розмір/довжину, а не на тип.

**Статус:** VERIFIED (джерело = immediate `0x1800`), але семантика поля UNRESOLVED; «Pc = data type» — **НЕ ПІДТВЕРДЖЕНО**.

## B.2 Producer 4-го поля `[r10+0x2513]`

```
0x01C042: 0x3B r24 <-> [r11+0x8592]     → r24 = mem (load)
0x01C04A: op0x13 r24 = f(r24, 0x180F)   → модифікація (маска/зсув, семантика op 0x13 не доведена)
0x01C056: 0x3B r24 -> [r10+0x2513]      ***
```

- Значення походить із **пам'яті** (`[r11+0x8592]`), а не з immediate → може залежати від стану.
- Кодек-залежність **не доведена** (немає порівняння/розгалуження в протрасованому вікні).
- Зв'язок із 3-м полем: спільне джерело `0x180F/0x1800` у константах — можливо, пов'язані (розмір/довжина).

**Статус:** producer VERIFIED (load + op 0x13), семантика — **UNRESOLVED**.

## B.3 Перший споживач: перепис звернень (весь образ)

| Поле | К-сть звернень | Сайти |
|---|---|---|
| `[r10+0x250D]` (Pa) | **1** | `0x01BEFA` (тільки запис) |
| `[r10+0x250F]` (Pb) | **1** | `0x01BF06` (тільки запис) |
| `[r10+0x2511]` | 2 | `0x01BF1C` (фаза 0 — ймовірно хибна), `0x01C052` (фаза 2 — валідна) |
| `[r10+0x2513]` | 2 | `0x01BF20` (фаза 0 — ймовірно хибна), `0x01C056` (фаза 2 — валідна) |
| `[r10+0x2515]` | 1 | `0x01BF3C` (op `0x3A`) |
| `[r10+0x250E]` | 1 | `0x057086` — **інший регіон**, інший `r10`, не наша структура |

**Ключовий факт: жодного читання (read-back) полів `0x250D/0x250F/0x2511/0x2513` у всьому образі не знайдено — лише записи.**

Безпосередньо після записів:

```
0x01C05A: C8A01800  op0x32 r5 = 0x1800
0x01C05E: E7FFFD95  op0x39 CALL  (rD=31, rA=31, imm=0xFD95)
```

- **CALL `0x01C05E`** — перша достовірна операція після запису заголовка; найімовірніша точка передачі.
- **Ціль CALL не декодується**: R16 встановив, що формат displacement для `op 0x39` не підтверджений (статистичний тест по 17 714 сайтах не зійшовся).
- Аргумент перед викликом: `r5 = 0x1800` (ймовірно розмір), і, схоже, `r10` як покажчик буфера.

**Статус:** точка передачі (CALL `0x01C05E`) — VERIFIED; адресат і подальша обробка — **UNRESOLVED**.

## B.4 Intermediate buffer чи TX-facing?

**UNRESOLVED.** Аргументи обох сторін:

- *За проміжний буфер:* відсутність CPU read-back; наявність CALL одразу після запису (типова передача покажчика далі).
- *За TX-facing:* відсутність read-back також узгоджується з тим, що буфер читає DMA/апаратура, а не CPU.
- Окрема ознака: на `0x01BF52` є `ori r10, r10, 0x2514` — тобто покажчик пересувається **за** заголовок (0x2514 = наступний за 0x2513), що узгоджується з «записати заголовок → писати payload далі». Але адресно це **до** `0x01C052`, тому належність до того самого базового блоку не доведена.

Без адресата CALL класифікувати неможливо. Не називати `[r10+…]` SPDIF FIFO.

## B.5 AC3/DTS статична розбіжність

**Кодек-залежного control flow у протрасованому шляху НЕ знайдено.**

- `Pa = 0xF872`, `Pb = 0x4E1F` — кодек-незалежні константи стандарту.
- 3-є поле отримує **фіксований immediate `0x1800`** — не залежить від codec ID, таблиці чи DTS/AC3 стану.
- `op 0x32` ніколи не містить `0x0B`/`0x01` (IEC data-type) у всьому образі → гіпотеза «Pc = 0x0B DTS / 0x01 AC3» **не має підтвердження** в цьому шляху.
- 4-е поле походить із пам'яті — залежність від кодека можлива, але не доведена.

## B.6 Підсумкові статуси

| Твердження | Статус |
|---|---|
| `Pa 0xF872 → [r10+0x250D]` | **VERIFIED** |
| `Pb 0x4E1F → [r10+0x250F]` | **VERIFIED** |

| 3-є поле = Pc (data-type 0x0B/0x01) | **НЕ ПІДТВЕРДЖЕНО** (ймовірно хибно) |

| Проміжний буфер vs TX FIFO | **UNRESOLVED** |

| Абсолютна база r10 | **UNRESOLVED** (не пріоритет) |

# R25-C — resolve `CALL` @ `0x01C05E`

**Мета:** встановити, що відбувається після побудови структури.
**Режим:** тільки workspace. Без runtime/device/patch.

## C.1 Спроба довести encoding `op 0x39` емпірично

Використано незалежно підтверджені print-CALL сайти (DEC-образ, з R16 / dec_state_transition):

| Site | Word | op | rD | rA | imm |
|---|---|---|---|---|---|
| `0x0124A6` | `E423D088` | 0x39 | 1 | 3 | `0xD088` |
| `0x021FD2` | `E7FFFF3F` | 0x39 | 31 | 31 | `0xFF3F` |
| `0x021FE2` | `E421DA10` | 0x39 | 1 | 1 | `0xDA10` |
| `0x022058` | `E421D924` | 0x39 | 1 | 1 | `0xD924` |

Гіпотеза: якщо ці виклики йдуть у спільну print-функцію, то під правильною формулою
displacement усі чотири мають дати одну адресу. Перевірено 8 формул
(`PC{+0,+2,+4} + (imm<<2 | imm<<1 | imm)`, зі знаком):

```
PC+4+(imm<<2) -> 0x66ca, 0x21cd2, 0x18826, 0x184ec
PC+4+(imm<<1) -> 0xc5ba, 0x21e54, 0x1d406, 0x1d2a4
PC+4+imm      -> 0xf532, 0x21f15, 0x1f9f6, 0x1f980
... (усі 8 варіантів) — жоден не дає спільної цілі
```

**Спільної цілі немає.** Ба більше, сайти мають різні `rD`/`rA` (`1/3`, `31/31`, `1/1`, `1/1`),
тому передумова «одна й та сама функція» сама по собі не була обґрунтована — R16 підтверджував
лише те, що `op 0x39` є *call-подібною* інструкцією, а не спільність адресата.

Це узгоджується з R16, де систематичний статистичний тест по 17 714 CALL-сайтах
для `PC±sign16` (byte і halfword) **не зійшовся**.

## C.3 Вердикт

```
UNRESOLVED: CALL target cannot be proven statically
```

- Формат displacement для `op 0x39` не підтверджений емпірично.
- Немає symbol/relocation evidence (образи сирі).
- Локальний control-flow context не дає адресата: після `0x01C05E` йде код,
  для якого не встановлено, чи це продовження тієї ж функції, чи інша функція
  (межі функцій у змішаному 16/32-bit потоці не визначені).

**Наслідки для попередніх висновків:**

- Класифікація callee (A/B/C) — **неможлива** без адресата.
- Твердження «перший споживач = CALL `0x01C05E`» лишається **VERIFIED як точка передачі**,
  але адресат і характер обробки — **UNRESOLVED**.
- Питання «intermediate buffer vs TX-facing» лишається **UNRESOLVED** (B.4 без змін).

**Що могло б зрушити (не виконувалось):**
1. Визначити межі функцій у змішаному 16/32-bit AEON-потоці (наприклад, за сталою
   послідовністю прологу/епілогу), далі — зіставити CALL-сайти з входами функцій.
2. Знайти пару «caller/callee», де callee ідентифікується незалежно (наприклад, за
   власною сигнатурою — наявністю матеріалізації рядка/константи всередині).
3. Runtime-підтвердження (після окремого дозволу): прочитати блок
   `[r10+0x250D…0x2515]` під real DTS і real AC3 — це не вимагає знання адресата CALL.
