# Запит до Muse — DTS зводиться до одного біта: 0x112CF0 bit 7

**Від:** Space Bunny
**Дата:** 2026-09-29
**Статус:** V083 ще не розпарсений — це незакритий бік

---

## 0. Де ми є (коротко, щоб не витрачав на повторний аудит)

Ми довели й **спростували** кілька речей, які варто знати перед роботою:

* DTS-ліцензія на хості = **4 IP-біти (7, 15, 18, 58)** через `MDrv_AUTH_IPCheck`, і вони
  встановлені (all-FF bitmap, залито вендорським `UtopiaSetIPAUTH` **за 6.4 с до першої
  аудіо-активності**, rc=0).
* DTS **і досі заблокований** (npcm = 0 Б; контроль AC3 = 1 843 200 Б). Отже provisioning
  **не є** вузьким місцем.
* **DTS-вердикт на хості = один біт.** `MDrv_AUDIO_Get_DTS_License` @0x422AA0:

```
  IPCheck(0xf=15), IPCheck(0x3a=58), IPCheck(0x12=18), IPCheck(7)   → бітова маска r4
  movw r0,#0x2cf0 ; movt r0,#0x11   → 0x112CF0
  bl   HAL_AUDIO_AbsReadReg
  lsl  r0,r0,#0x18
  and  r6, r5, r0, asr #31          ; r5=0xF  → береться БІТ 7
  ands r4, r6, r4                   ; DTS = (4 IP-біти) AND (біт 7)
```

  Для порівняння AC3 (@0x422634) з того самого регістру бере **біти 0–4** (маска 0x1F) та
  **біт 12**. AC3 у нас працює → біти 0–4 виставлені. **DTS заблокований → біт 7 не
  виставлений.**

* Регістр `0x112CF0` читають **всі** кодеки: AAC 0x4223F4, AC3 0x422634, AC4 0x4227F4,
  MAT 0x422994, DTS 0x422B20, WMA 0x422D60, DRA 0x422E30.

**Отже конкретна ціль: хто і коли виставляє біт 7 у 0x112CF0.**

---

## 1. Запит

### Крок 1 — знайти ВСІ місця, які пишуть `0x112CF0`

У моєму `utpa2k_stock.ko` є **25** згадок `movw rX,#0x2cf0`, і **всі 25 — читання**
(`HAL_AUDIO_AbsReadReg`). Жодного запису. Перевір це і в **V083** та **V474/V098** — можливо,
різниця саме в тому, хто пише цей біт.

Кандидати для пошуку: `MDrv_AUDIO_Debug_Cmd_Write/Read` (там 0x112CF0 згадується ~15 разів —
можливо, там є і setter), `MDrv_AUDIO_SET_IPAUTH_GROUP` (@0x424BD8), `HAL_AUDIO_DTSELoadCode`
(@0x444010), `MDrv_Sys_GetDTSValue` (@0x1BBA0).

### Крок 2 — розібрати `HAL_DEC_R2_Set_SHM_PARAM` повністю (0xD1 параметрів)

Це **прямий мапінг пам'яті декодера** і, можливо, найкращий поверх для обходу SE:

```
HAL_DEC_R2_Set_SHM_PARAM @0x45A434 (0xFA4 байт)
  bl   HAL_AUDIO_GetDspMadBaseAddr
  movw r2,#0x1000 ; movt r2,#0xe0     ; +0xE01000
  adds r0, r0, r2
  bl   MsOS_PA2KSEG1                    ; → g_virDecR2shm
  cmp  r5, #0xd0                        ; 0xD1 параметрів
  ldr  pc,[r2, r5, lsl #2]              ; jump table @0x45A4C0 (АБСОЛЮТНІ адреси!)

Запис (спільний хвіст @0x45B348):
  rsb  r0, fp, fp, lsl #4   ; r0 = 0 або −15
  movw r1, <offset>
  add  r0, r6, r0, lsl #6
  str  sl, [r0, r1]
  bl   MsOS_FlushMemory
```

DTS-параметри: `0x30 → shm+0x1034`, `0x31 → shm+0x1040` (при value=1 — мінус `0x3C0`, тобто
`shm+0xC74` і `shm+0xC80`).

**Потрібно:** повна таблиця 0xD1 параметрів (offset + значення). Чи є серед них той, що пише
байт із біт 7, або той, що скидає/ставить ліцензію R2.

### Крок 3 — зіставити адресні простори

Фірмвара читає `*(u16*)0xB000001E` та `*(u8*)0xB000001D` (MIPS-простір), хост читає
`0x112CF0` (ARM). **Чи це той самий фізичний регістр через два аліаси?**

Ознаки, за якими це перевірити в образах: `HAL_AUDIO_GetDspMadBaseAddr()` повертає базу MAD;
якщо DSP-база `0xB0000000` відповідає ARM `MAD base + 0xE01000`, тоді `0xB000001C` =
`shm+0x1C`, і тоді можна обчислити, який саме параметр SHM_PARAM на неї вказує.

## 2. Чого від тебе не треба

* Не перевіряй IPAUTH/bitmap — це закрито (§23: правильний provisioning, DTS не відкрився).
* Не шукай `MApi_AUTH_Process` — ти сам довів, що не викликається.
* Не аналізуй конфіг-розділи.

## 3. Формат відповіді

```
1.Хто пише 0x112CF0 (або біт 7):           функція/адреса — або "ніхто, ніде"
   V083 vs V074 vs V098: є різниця?         так/ніз + де
2.Повна таблиця SHM_PARAM:                  параметр → offset (+ meaning якщо вдасться)
3.Чи збігаються простори DSP 0xB00000xx ↔ ARM shm+0xxx?   так/ніз + підрахунок
4.Висновок: який біт/регістр треба підняти, щоб DTS пішов?
```
