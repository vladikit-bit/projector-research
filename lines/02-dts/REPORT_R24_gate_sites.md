# R24 — Спроба NEXT SINGLE TEST: блокер Ghidra + карти сайтів license-поля

**Дата:** 2026-09-08 · **Образ:** `r2img/mst_codec_r2_MS12V22.bin` (DEC/CODEC R2)
**Обмеження:** статично; жодних runtime-захоплень, DM-дампів, патчів, змін конфігурації/EDID.
**Нового toolchain не встановлено.**

---

## 1. БЛОКЕР: Ghidra не може декодувати AEON

Перевірено `C:\ghidra_12.1.2_PUBLIC\Ghidra\Processors`:

```
ARM · MIPS · PowerPC · Xtensa
```

Мови **AEON немає** (`find -iname "*aeon*"` → порожньо). Отже запланований тест
«декодувати блок гейта `0x021f00–0x021fea` у Ghidra» **у зазначеному вигляді не виконується**.
Нічого не встановлювалося і не створювалося.

Замість декодування невідомих опкодів застосовано **вже доведені** idiom-и
(перевірені побайтово в R8 / R23-A.3 / R16 grid, а не за числовою схожістю):

| Idiom | Підтвердження |
|---|---|
| `LOAD` — op `0x3B`, rd/ra у бітах, imm16 = displacement | R8: `0x016F84 EC8B…`/`EEEC00FA` = `LD r23,0xFA(r12)`; R16 grid |
| `movhi` — op `0x30`, imm16 | R8/R23-A.3: `0x021FDA C0600281` → `movhi r3,0x0281` |
| `ori` — op `0x3F`, imm16 | R8/R23-A.3: `0x021FDE FC634904` → `ori r3,r3,0x4904` |
| `r12 = 0x21A000` (SHM window) | R8, доведено `movhi/ori` + field-value echo |

## 2. Результат A: рядок гейта має рівно ОДИН код-сайт

Пошук по всьому образу матеріалізації адреси `'Invalid Spdif license:%d, output_spdifSz:%d'`
(`movhi 0x0281` + `ori 0x4904` → `0x2814904`):

```
знайдено 1 сайт:
  0x021FDA: C0600281  movhi r3,0x0281
  0x021FDE: FC634904  ori   r3,r3,0x4904
```

Тобто print гейта існує в єдиному екземплярі — немає окремої «DTS-копії» цього виводу.
Мапінг file→DSP для цієї області: `+0x26D0000` (`0x144904 + 0x26D0000 = 0x2814904`).

Оточення сайту (BE-слова):

```
0x021FD6: EC8B02E6   LOAD  r4, 0x2E6(r11)      ← license-значення
0x021FDA: C0600281   movhi r3, 0x0281
0x021FDE: FC634904   ori   r3, r3, 0x4904      ← r3 = 0x2814904 (адреса рядка)
0x021FE2: E421DA10   op 0x39 (CALL)            ← виклик print
0x021FE6: E7FFFD43   op 0x39 (CALL)
```

Послідовність «читання license → матеріалізація рядка → CALL» узгоджується з
`printf("Invalid Spdif license:%d, output_spdifSz:%d", lic, sz)`.

## 3. Результат B: license-поле `+0x2E6` читається у П'ЯТИ місцях

R16 сканував лише регіон `0x021c00–0x022400` і бачив одне читання. По всьому образу
(op `0x3B`, imm `0x02E6`) їх **п'ять** — це новий факт:

| Адреса | Інструкція | Базовий регістр | Effective address |
|---|---|---|---|
| `0x01CA16` | `LOAD r24, 0x2E6(r13)` | r13 | невідома база |
| `0x021FD6` | `LOAD r4, 0x2E6(r11)` | r11 | невідома база ← **сайт print** |
| `0x02F64C` | `LOAD r23, 0x2E6(r12)` | **r12 = 0x21A000 (SHM)** | **0x21A2E6** → зі зсувом −2: ARM SHM **+0x2E4** |
| `0x0BA930` | `LOAD r24, 0x2E6(r11)` | r11 | невідома база |
| `0x12921E` | `LOAD r17, 0x2E6(r1)` | r1 | невідома база + **обхід масиву** |

**Найважливіше — `0x02F64C`.** Тут license-значення читається з **SHM-вікна** (`r12`,
база доведена в R8), тобто з області output-параметрів, куди пише ARM. Це перший прямий
зв'язок license-перевірки зі SPDIF output-parameter path.

**`0x12921E`** — одразу за ним йде серія завантажень з кроком 4:
`+0x2EA`, `+0x2EE`, `+0x2F2`, `+0x2F6` — це обхід масиву (ймовірно, `lic[%d,%d,%d]`,
про який згадує R16).

---

## 4. Спостереження (НЕ доведено)

Слово з op `0x03` з'являється безпосередньо після двох читань license:
`0x0BA934` (після `0x0BA930`) і `0x02F650` (після `0x02F64C`, SHM-читання).
Це узгоджується з перевіркою/переходом за license-значенням, **але семантика op `0x03`
не доведена** (R16 перевірив OR1K-стиль `rd=ra=0` — не підтвердилося). Тому це
лише структурна ознака, а не доказ умовного переходу.

---

## 5. Статус decision tree

Однозначно вибрати гілку R24-B / R24-C **наразі неможливо**: невідома інструкція
порівняння/переходу і те, чи виконується гілка під DTS.

Що вже звузилося:
- print гейта — один, отже «другого, DTS-специфічного» виводу не існує;
- license-значення споживається щонайменше у 5 місцях, одне з яких — у SHM
  output-parameter path (`0x21A2E6` ↔ ARM `+0x2E4`).

---

## 6. Наступний крок (потребує рішення)

Варіанти, жоден не потребує нових інсталяцій:

1. **Декодувати op `0x03`** у вузькому контексті (лише навколо 5 сайтів) — спроба
   встановити, чи це перехід, через структурний аналіз цілей: чи вказують його поля
   на адреси всередині відомого блоку. Ризик: це межує з numeric guessing.
2. **ARM-бік у Ghidra** (підтримується): перевірити, хто записує SHM `+0x2E4`
   (відповідник `0x21A2E6`) — тобто який host-параметр є джерелом license-значення.
   Ghidra для ARM доступна повністю.
3. Зіставити `0x21A2E6` з уже відомою картою параметрів (R8: `+0xf8`=0x6e,
   `+0x104`=0xa0, тощо) — визначити номер параметра для `+0x2E4`.

Найперспективніше — **варіант 2/3**: вони дають достовірний ARM-аналіз (Ghidra підтримує
ARM) і не потребують декодування невідомого AEON.
