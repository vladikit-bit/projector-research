# REPORT R12 — конкретний ланцюг розбіжності AC3 vs DTS (від runtime-якорів R11)

**Пристрій:** Thundeal TD98 Pro / C50A (MStar MT5889) · Android 11 · kernel 4.19.116
**Дата:** 2026-09-07
**Базовий стан:** `utpa2k.ko` = `f44ad0a4…`, `mik.ko` = `03fc2c0d…` — **не змінювались**.
**Режим:** static + offline-аналіз вже наявних runtime-дампів. **Нічого не патчилось,
на пристрій не заходили.**
**Вхід:** R11 (`read_dsp_sram_type` / `write_dsp_sram_type`, DM-дампи `r11_out/dm2_*`, `dm3_*`),
R10 (ліцензійний gate в DEC-образі), R8 (завантаження образів, `0x4d0=4` → MS12V22).

---

## 0. Короткий результат

Знайдено **конкретну функцію та конкретну умову**, і — що важливіше — тепер є
**прямий runtime-доказ місця обриву**, а не лише непрямі ознаки:

> **AC3:** декодер → **writer IEC61937-подібного burst-буфера в DEC DM `0x0A00…`
> перезаписує його безперервно**.
> **DTS:** декодер працює, але **writer у цей буфер не входить узагалі** — буфер
> зберігає **байт-у-байт попередній AC3-burst** (`F872 4E1F | 0001 | 3000 | 0B77 …`) і
> не змінюється ≥90 с. Це не «супресія на виході», це **невиклик writer-а**.

І головне уточнення до гіпотези R8/R10:

> **Увесь SPDIF output/license-шлях живе в DEC DSP, а не в SND.**
> У `mst_snd_r2_MS12V22` немає жодного з рядків `dts m6 init ok`, `dts_licensee`,
> `Invalid Spdif license`, `output_spdifSz`, `dec play !!` — вони є **тільки** в
> `mst_codec_r2_MS12V22` (DEC). Тому шлях «DEC → SND transcoder → SDO»,
> який ми припускали, **на цьому пристрої не є тим, що формує SPDIF-вихід**.

## 1. Який DSP ми взагалі бачимо через `read_dsp_sram_type`

Декодовано `_HAL_MAD2_DBG_CMD_Read_DSP_sram` @ VA `0x40adc4`:

```
0x0040ae54: uxth  fp, r0      ; addr  -> усікається до 16 біт (0..0xFFFF)
0x0040aea0: uxth  r4, r4
0x0040aea4: cmp   r4, #1      ; type: 0 = PM, 1 = DM
```

Параметри команди: **тільки** `type`, `addr`, `len` — **ніякого селектора ядра немає**.

Наслідок: addr — це 16-бітне зміщення в DM. З R8 відомо, що при `0x4d0=4` образи
кладемо так: **DEC = `MAD(2)+0`**, **SND = `MAD(2)+0x700000`**. 16-бітна адреса
не може дотягнутись до `+0x700000`, отже **команда бачить лише DEC**.

Це ж підтверджує вміст: у дампах присутній стан DTS-декодера (`dts m6`), лічильники
декодера та — як показано нижче — DM-база `0x1c011000`, яку використовує саме
DEC-образ.

> **Висновок (STRONGLY SUPPORTED):** runtime-DM, який ми читаємо/пишемо, — це **DEC DSP**.
> **SND DSP через цей інтерфейс недосяжний.** Це обмеження треба мати на увазі для
> всіх подальших SND-експериментів.

## 2. Алгебра DM-вікна DEC (підтверджено вперше)

У DEC-образі `r8_out/mst_codec_r2_MS12V22.bin` на **phase 2** (зсув ≡ 2 mod 4)
інструкції декодуються зв'язно. У регіоні `0x021eaa`:

```
021eaa  c3201c01   movhi r25, r0, 0x1c01     ; r25 = 0x1c010000
021eae  ff391000   ori   r25, r25, 0x1000    ; r25 = 0x1c011000
```

Це точно покажчик, який R10 бачив у gate-коді. Отже:

```
DM-адреса N   ↔   DSP VA  0x1c010000 + N
```

Перелік усіх абсолютних звернень DEC у вікні `0x1c01xxxx`
(`tools/r12_dmxref.py`, 118 пар `movhi+ori`):

| VA | DM | скільки разів |
|---|---|---|
| `0x1c011000` | **0x1000** | **20** |
| `0x1c011e10` | 0x1e10 | 19 |
| `0x1c011ad0` | 0x1ad0 | 14 |
| `0x1c011bc8` | 0x1bc8 | 13 |
| `0x1c011080` | 0x1080 | 12 |
| `0x1c0126b0` | 0x26b0 | 11 |
| `0x1c011cf8/1cfc/1d00/1d08/1d0c` | 0x1cf8… | по 1 |

**Важливо:** `0x1c010900–0x1c010b50` (тобто DM `0x0900–0x0B50`) у цьому списку
**відсутні**. Тобто вихідний буфер адресується **не абсолютно**, а через базовий
регістр + зміщення (динамічний дескриптор буфера). Це узгоджується з тим, що
`0x1c011000` (DM 0x1000) — база стану, яку код піднімає перед кожним зверненням.

## 3. Головний runtime-якір: що насправді лежить у DM `0x0A00`

R11 стверджував «IEC61937 burst header region (DM 0x0A00: `F872 4E1F 0001 …`)»,
але не наводив вміст. Перевірив по всіх дампах: синхрослова зустрічаються **лише у
`dm2_*`** (вікно `0x0000–0x2000`). Ось верхні 16 біт кожного 24-бітного DM-слова:

| DM | idle | dts | dtsb | ac3 | ac3b | тлумачення |
|---|---|---|---|---|---|---|
| 0x0A00 | `f872` | `f872` | `f872` | `0000` | `0000` | **Pa** IEC61937 |
| 0x0A01 | `4e1f` | `4e1f` | `4e1f` | `4e1f` | `0000` | **Pb** IEC61937 |
| 0x0A02 | `0001` | `0001` | `0001` | `36db` | `0000` | **data-type = 0x0001 → AC3** |
| 0x0A03 | `3000` | `3000` | `3000` | `0000` | `0000` | довжина 0x3000 = 12288 біт = 1536 байт |
| 0x0A04 | `0b77` | `0b77` | `0b77` | `0000` | `0b77` | **sync AC3 (0x0B77)** |
| 0x0A05 | `2933` | `9611` | `9611` | `0000` | `e7cf` | payload… |

**Це повний, коректний AC3 IEC61937-burst**: Pa `F872`, Pb `4E1F`, тип `0x0001` (AC3),
довжина 1536 байт, далі кадр із AC3-sync `0x0B77`.

Інтерпретація трьох станів:

* **idle / dts / dtsb** — буфер містить **той самий** залишковий AC3-burst
  (`0x0A05` відрізняється, бо між захопленнями встигло програтись AC3).
  **Для DTS буфер не переписується взагалі.**
* **ac3 / ac3b** — буфер **активно перезаписується потоком** (Pa збито в `0000`,
  далі живі значення) — ознака безперервного запису.

> ### ⚠ Про назву регіону
> Я **не називаю** `0x0900–0x0B50` «IEC61937 buffer» остаточно. Доказів рівно стільки:
> у `0x0A00–0x0A05` лежить послідовність, що точно збігається з IEC61937
> Pa/Pb/data-type/length + AC3 sync. Це **дуже сильний** збіг, але формально
> підтверджена роль — «вихідний буфер SPDIF, куди AC3 пише, а DTS ні».
> Регіон `0x0900–0x0968` має інший характер (бітові шаблони `4444/9249/2492/4924`
> = циклічний зсув на 1 біт) — це **не** payload того ж кадру; його роль не з'ясована.

## 4. Новий аналіз: **статичний** differential (R11 робив лише динамічний)

R11 порівнював «що змінюється між двома зрізами». Я порівняв **значення AC3 проти DTS
поадресно** у повних дампах `dm3_ac3.txt` / `dm3_dts.txt` (по 65537 адрес):

* відрізняються **1982** адреси, 124 кластери;
* більшість (0x4800–0xFFFF) — це циклічні PCM/audio-буфери → відрізняються природно;
* **структурно значущі** кластери лише в молодших адресах:

```
0x0900-0x0903  0x0918-0x0933  0x0949-0x0962
0x0a00-0x0a17  0x0a2c-0x0b23 (240 слів!)  0x0b38-0x0b53  0x0b69-0x0b84
0x0b99-0x0bb4  0x0bca-0x0be3            <-- періодичні блоки по ~22 слова, крок 0x31
0x0f41-0x0f59  0x0f71-0x0f7d
0x0fe8-0x100f  0x103f  0x105b-0x1060  0x1074-0x1077  0x109a-0x10cd
```

Періодичні 22-словні блоки з кроком `0x31` у `0x0b38–0x0be3` виглядають як
**повторювані кадри/burst-структури** — ще один аргумент, що `0x0900–0x0B50` — це
кільцевий вихідний буфер.

**Статичні відмінності стану (AC3 / DTS), які R11 не фіксував як статичні:**

| DM | AC3 | DTS | коментар |
|---|---|---|---|
| 0x0FE8 | `000006` | `000000` | hot (DSP переписує) |
| 0x0FEB | `000042` | `000000` | hot |
| 0x0FF3 | `000040` | `000000` | hot |
| 0x0FF6 | `000008` | `000000` | hot |
| 0x0FF9 | `000020` | `000000` | hot |
| 0x0FEC / 0x0FED | `0c00` / `0c08` | `0c00` / `0c00` | дельта +8 лише в AC3 |
| 0x0FF4 / 0x0FF5 | `0e00` / `0e58` | `0e00` / `0e00` | дельта +0x58 лише в AC3 |
| 0x0FF8 / 0x0FF9 | `0609e0` / `0609f8` | `048a00` / `048a00` | схоже на покажчики буфера |
| **0x105B** | `000004` | `000000` | R11 вже писав 4 → без ефекту |
| 0x105E | `000001` | `000000` | R11 вже писав 1 → без ефекту |
| **0x109B** | `0e15cc` | **`7fffff`** | DTS = максимум 24 біт («нема/не задано») |
| **0x10A5** | `000000` | **`7fffff`** | те саме |
| 0x10C5 / 0x10C7 / 0x10CB / 0x10CD | `05` | `00` | R11 вже писав 5 → без ефекту |
| 0x10C8 | `0140` | `003c` | схоже на розмір/рівень (320 vs 60) |

`0x109B` і `0x10A5` = `0x7fffff` у DTS — **найцікавіші нові кандидати**: значення
«усе одиниці» типово означає «не ініціалізовано / немає ліміту / невалідно», і їх
R11 не пробував.

## 5. Де насправді живе DTS-output шлях: **DEC, не SND**

Пошук по обох образах (rodata VA = file + `0x26CD000` для DEC, `+0x24F0000` для SND):

| рядок | DEC | SND |
|---|---|---|
| `dts m6 hook ok` | ✅ `0x00146ac5` | ❌ |
| `dts m6 init ok,dts_licensee=%d, lbr_licensee=%d, xll_licensee=%d, transcoder_licensee=%d` | ✅ `0x00146ad5` | ❌ |
| `Invalid Spdif license:%d, output_spdifSz:%d` | ✅ `0x00144904` | ❌ |
| `Invalid Hdmi license:%d, output_spdifSz:%d` | ✅ `0x00144843` | ❌ |
| `dec play !!` | ✅ `0x00141be3` | ❌ |
| `Mstar_DTS_Hdmi_Packer error=%x` | ✅ `0x001439ee` | ❌ |
| `ap->dtsenc_owner=%d, snd_r2_dtsenc=%d, snd_dsp_dtsenc=%d` | ✅ `0x00146a10` | ❌ |
| `OTP fail : 0x%x, 0x%x, 0x%x` | ❌ (1 випадковий збіг) | ✅ `0x1287c3` |

**Увесь SPDIF/license/output-шлях зосереджений у DEC.** SND має власні DTS-модулі
(`dtsX_core2`, `dts_virtualx`, `dtsM6_enc`, `DTSX_CORE2_API_SDO_Packer`,
`SDO_SpdifPacker_SAPI_*`), але **жодного** коду формування SPDIF-виходу чи ліцензійного
gate.

Також знайдено і підтверджено **print-сайт ліцензій** у DEC (код file `0x01e606–0x01e682`):

```
01e5de  c1401c01  movhi r10, 0x1c01
01e5e6  fd4a1000  ori   r10, r10, 0x1000      -> r10 = 0x1c011000  [DM 0x1000]
01e5ea  ec8a0cf6  ld/st r4, 0x0cf6(r10)       -> DM 0x1CF6
01e5ee  ecaa0cee  ld/st r5, 0x0cee(r10)       -> DM 0x1CEE
01e5f2  ecca0cf2  ld/st r6, 0x0cf2(r10)       -> DM 0x1CF2
01e5f6  c0600281  movhi r3, 0x0281
01e5fa  fc6339ee  ori   r3, r3, 0x39ee        -> "Mstar_DTS_Hdmi_Packer error=%x\n"
01e5fe  e4224dd8  call
...
01e606  c0600281  movhi r3, 0x0281
01e63a  fc633a10  ori   r3, r3, 0x3a10        -> "ap->dtsenc_owner=%d, snd_r2_dtsenc=%d, snd_dsp_dtsenc=%d\n"
01e642  e70083a0  call
...
01e67a  fc633ae2  ori   r3, r3, 0x3ae2        -> "…dts_licensee=%d, lbr_licensee=%d, xll_licensee=%d, transcoder_licensee=%d"
```

Примітка: DM `0x1CEE/0x1CF2/0x1CF6` **однакові в AC3 і DTS** (їх немає у списку
відмінностей) → це **не** ліцензійні змінні, а стан HDMI-пакера.

## 6. Ланцюги: AC3 vs DTS

### AC3 — працює

```
ES AC3 (offload, ENCODING_AC3)
 → DEC DSP: "CPU MS12V2 ddp hook ok" / "CPU MS12V2 ddp init ok"   [лога R11, тільки AC3]
 → DEC output stage: ЛІЦЕНЗІЙНИЙ GATE ПРОЙДЕНО (Dolby MS12V2 не має DTS-подібного gate)
 → writer SPDIF-буфера DEC DM 0x0A00..:
       F872 4E1F | data-type 0x0001 (AC3) | len 0x3000 | 0B77 (AC3 sync) | payload…
 → буфер безперервно перезаписується (dm2_ac3: Pa збито живими даними)
 → SPDIF TX → AVR locks DD
```

### DTS — обрив

```
ES DTS (offload, ENCODING_DTS)
 → DEC DSP: "dts m6 hook ok" / "dts m6 init ok,
             dts_licensee=0, lbr_licensee=0, xll_licensee=0, transcoder_licensee=0"
 → ДЕКОДЕР ПРАЦЮЄ: "dec play !!", cpt/elaplsed ростуть, pcm/es/cB лічильники йдуть  [R11]
 → DEC output stage: 'Invalid Spdif license:%d, output_spdifSz:%d'
       → output_spdifSz = 0
 → writer SPDIF-буфера НЕ ПИШЕ НІЧОГО:
       DM 0x0A00.. зберігає попередній AC3-burst байт-у-байт ≥90 с  [dm2_dts vs dm2_dtsb]
       навіть не обнуляється
 → SPDIF TX не має кадрів → тиша, AVR не ловиться
```

### Конкретна відсутня умова

> **DEC DSP вимагає ненульову DTS-ліцензію (`dts_licensee` і/або `transcoder_licensee`)
> для запуску SPDIF output stage. На цьому пристрої всі чотири = 0, тому
> `output_spdifSz = 0` і writer вихідного буфера не виконується.**

Це **не** «DTS не доходить до SND transcoder». Обрив **до** transcoder/SDO — усередині
DEC, між виходом декодера та SPDIF output writer-ом.

## 7. SND: реальний шлях чи мертвий код?

Запитання з пріоритетом. Статус — **швидше мертвий/не задіяний, але доказ непрямий**:

| ознака | результат |
|---|---|
| SND-логи містять `dts` | **0 згадок** і в AC3, і в DTS (`r11_snd_*.log`) |
| SND-логи містять `snd_r2_dtsenc` / `dtsenc_owner` | **0** |
| SND-логи містять будь-які SPDIF/non-PCM рядки | **0** (R11: debug-gated off) |
| У SND-образі є DTS-модулі | ✅ `dtsX_core2`, `DTSX_CORE2_API_SDO_Packer`, `SDO_SpdifPacker_SAPI_*`, `DTSX_Transcoder` |
| У SND-образі є SPDIF/license-код | ❌ немає жодного з §5 |

**Чесна оцінка:** відсутність prints у SND **слабкий** доказ, бо SPDIF-prints у SND
загалом вимкнені debug-опцією. Але в поєднанні з тим, що (а) весь SPDIF/license-код у
DEC, (б) DEC сам має `snd_r2_dtsenc`/`dtsenc_owner` (тобто DEC керує тим, чи віддавати
DTS-кодування в SND), (в) у DEC є власний `Mstar_DTS_Hdmi_Packer` — картина така:

> **Для SPDIF-виходу DTS на цьому пристрої SND-шлях не задіюється. Рішення
> приймається в DEC, і воно блокується ліцензійним gate до будь-якої передачі в SND.**

## 8. Походження ліцензій — що нового в R12

* `dts m6 init ok, …licensee=0…` друкується **в обох** кодеках → це **module-init
  стан**, а не рішення під час відтворення. Тому «увімкнути ліцензію під час гри»
  не вийде — треба ре-ініт (`play type changed → decoder re-init!!`).
* `Invalid Spdif license` **не друкується ні в AC3, ні в DTS** (0 входжень) —
  gate-принт теж debug-gated, тож його не можна використати як runtime-сигнал.
* **DEC-образ не містить OTP-коду** (єдиний збіг `OTP` — у форматному рядку
  `' %x\n'`). Натомість **SND містить OTP-машинерію і вона падає**:
  `OTP fail : 0x1, 0x1000, 0xff00` (R11: фоновий шум, не корелює з кодеком).
  Це узгоджується з моделлю «ліцензія ніколи не доставляється», але **причинний
  зв'язок SND-OTP → DEC-licensee не доведено**.

**Статус因果-ланцюга (чесно):**

```
licensee=0 → 'Invalid Spdif license' → output_spdifSz=0 → немає запису в буфер
```
* `licensee=0` — **PROVEN** (runtime log).
* `output_spdifSz=0 → буфер не пишеться` — **PROVEN** (вміст DM 0x0A00 ідентичний ≥90 с).
* `licensee=0 → Invalid Spdif license` — **NOT PROVEN** (принт вимкнений; зв'язок
  виводиться з положення gate-коду між виходом декодера та writer-ом).
* `звідки береться licensee` — **UNRESOLVED** (R10 закрив ARM-джерела; R11 закрив
  одиничні DM-прапори; DEC не має OTP-коду).

## 9. Що робити далі (в порядку цінності)

1. **DM-write по нових кандидатах з ре-інітом**: `0x109B` і `0x10A5`
   (DTS = `0x7fffff`, AC3 = `0x0e15cc` / `0x000000`), а також пари
   `0x0FEC/0x0FED` і `0x0FF4/0x0FF5` (дельта лише в AC3). Обов'язково з
   **ре-інітом декодера** (play/stop), інакше значення просто не перечитується —
   саме тому проби R11 не спрацювали.
2. **Знайти адреси licensee-змінних**: код навколо DEC file `0x01e65e–0x01e682`
   (`movhi r23,0x0001` + `op32 …0x0870` + `op03 r4,r23,0x0206` прямо перед
   ori на рядок licensee) — це завантаження аргументів принта. Потрібен добудований
   16-бітний op decoder **лише для цього вікна** (~0x40 байт), не для всього образу.
3. **Увімкнути SPDIF-prints**: знайти SND debug-option, що відкриває
   `[SPDIF] spdif ISR … nonpcm_sel` (`r2_log_dbg_option` @ VA `0x409a8c`) — це дасть
   пряме спостереження SPDIF-стану по кодеках і закриє питання SND.
4. **PM-read** (`read_dsp_sram_type=0`) — звірити running PM з
   `aucode_adec_r2_MS12V22.bin` (R11 §6.3).

Не рекомендую: повний AEON RE, brute-force branch targets, повторне перерахування
SND SHM-полів — ці тупики вже закриті.

## 10. Класифікація достовірності

| твердження | статус |
|---|---|
| `read_dsp_sram_type` бачить DEC, addr усікається до 16 біт, без селектора ядра | **PROVEN** |
| DM-вікно DEC: `N ↔ 0x1c010000 + N` | **PROVEN** (movhi/ori в коді + збіг з R10) |
| Увесь SPDIF/license/output код — у DEC, у SND його немає | **PROVEN** (пошук рядків) |
| DM `0x0A00–0x0A05` містить валідний AC3 IEC61937 burst (Pa/Pb/type/len/sync) | **PROVEN** (дампи) |
| Для DTS цей буфер не переписується ≥90 с | **PROVEN** (dm2_dts vs dtsb; dm3_dts) |
| Для AC3 буфер переписується безперервно | **PROVEN** |
| Обрив — між виходом DEC-декодера та SPDIF output writer-ом | **PROVEN** |
| Конкретна умова: нульова DTS-ліцензія → `output_spdifSz=0` | **STRONGLY SUPPORTED** |
| SND DTS transcoder/SDO не задіюється для SPDIF | **SUPPORTED, не доведено** (prints вимкнені) |
| Звідки DSP бере licensee | **UNRESOLVED** |
| Роль регіону `0x0900–0x0968` | **НЕ З'ЯСОВАНО** |
