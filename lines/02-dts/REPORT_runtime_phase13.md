# REPORT R13 — локалізація writer-а burst-у та джерел `dts_licensee`

**Пристрій:** Thundeal TD98 Pro / C50A (MStar MT5889) · Android 11
**Дата:** 2026-09-07
**Режим:** static only. **Нічого не патчено, ніяких DM-write, пристрій не чіпався.**
**Вхід:** R12 (DM-вікно `N ↔ 0x1c010000+N`, burst в DM `0x0A00`, DEC-only output code),
R11 (дампи), R10 (ліцензійний gate).
**Обмеження сесії:** `adb` у цьому середовищі відсутній → **PM read (п.5) виконати неможливо**, перенесено.

## 1. Print-site `dts_licensee` (DEC file 0x01e65e–0x01e682)

### 1.1 Фаза підтверджена

Три жорсткі якорі лежать на **одній фазі ≡ 2 mod 4**, отже тут чистий 32-бітний потік:

```
0x01e606  c0600281  movhi r3, r0, 0x0281      r3 = 0x02810000
0x01e63a  fc633a10  ori   r3, r3, 0x3a10      "ap->dtsenc_owner=%d, snd_r2_dtsenc=%d, snd_dsp_dtsenc=%d\n"
0x01e67a  fc633ae2  ori   r3, r3, 0x3ae2      "k,dts_licensee=%d, lbr_licensee=%d, xll_licensee=%d, transcoder_licensee=%d"
```

**Уточнення до R12:** вказівник формату `0x02813ae2` = file `0x146ae2` — це **зсув +13 усередину**
повного рядка `dts m6 init ok,dts_licensee=…` (file `0x146ad5`). Тобто реально друкується
формат **`dts_licensee=%d, lbr_licensee=%d, xll_licensee=%d, transcoder_licensee=%d`**,
а префікс `dts m6 init ok,` походить з сусіднього рядка/принта. Лог-рядок у R10/R11
відповідає конкатенації цих двох.

### 1.2 Потік безпосередньо перед `ori r3, 0x3ae2`

```
0x01e65a  d46b0172  op35  r3 ,r11,0x0172   -> sw 0x0172(r11), r3   (ЗБЕРЕЖЕННЯ, а не запис у r3)
0x01e65e  c2f60001  movhi r23,r22,0x0001   r23 = 0x0001_0000
0x01e662  caf70870  op32  r23,r23,0x0870   r23 = 0x0001_0870        (op32 = ori-подібний, ВИВЕДЕНО)
0x01e666  0c970206  op03  r4 ,r23,0x0206   r4 <- [0x0001_0A76]      (op03 = load, ВИВЕДЕНО)
0x01e66a  e0ffc060  op38  r7 ,r31,0xc060
0x01e66e  0281caf7  op00  r20,r1 ,0xcaf7
0x01e672  ffff8177  ori   r31,r31,0x8177
0x01e676  8159813b  op20  r10,r25,0x813b
0x01e67a  fc633ae2  ori   r3 ,r3 ,0x3ae2   -> формат licensee
```

Два важливі висновки:

1. **`op 0x35` = збереження (`sw`)**, а не перезапис r3. Формат `sw imm16(rA), rB`:
   `d46b0172` → `sw 0x172(r11), r3`. Отже **аргументи принта передаються через блок
   аргументів у пам'яті за вказівником r11**, а не лише через регістри. Це пояснює, чому
   «чисті» регістрові трейси тут не сходяться.
2. З'явилося **третє вікно адрес — `0x0001xxxx`**, відмінне від rodata (`0x0281`)
   і DM (`0x1c01`).

### 1.3 Що можна стверджувати про 4 значення

```
dts_licensee        <- [0x0001_0A76 + k0]   (перше завантаження: r4 <- [r23 + 0x0206])
lbr_licensee        <- [0x0001_0A76 + k1]   (той самий шаблон op03/op05 по r23/r24)
xll_licensee        <- [0x0001_0A76 + k2]
transcoder_licensee <- [0x0001_0A76 + k3]
```

**Довіра:** `movhi r23,0x0001` — **PROVEN** (op 0x30, підтверджений раніше).
`r23 = 0x00010870` — **ВИВЕДЕНО** (op 0x32 семантично не підтверджений).
`r4 <- [r23+0x206]` — **ВИВЕДЕНО** (op 0x03 семантично не підтверджений).
**Чи збігається `0x0001xxxx` із простором, який ми бачимо як DM `0x0000–0xFFFF` — НЕВІДОМО.**

> **Чесний підсумок п.1:** чотири значення завантажуються **з пам'яті** (не константи,
> не результат функції безпосередньо в цьому вікні), з групи полів у вікні `0x0001xxxx`.
> Точні адреси вимагають підтвердження семантики op `0x32` і `0x03`.
> **Формулу `dts_licensee ← DM[0x....]` навести поки не можна.**

## 2. Writer burst-у — ЗНАЙДЕНО (найсильніший результат R13)

### 2.1 Константи IEC61937 справді присутні як immediates

Пошук `ori` з `rA = r0` (завантаження immediate) у DEC-образі:

| immediate | сайти (op 0x3f, rA=0) |
|---|---|
| **`0xf872` (Pa)** | `0x024c0c` (r24), `0x02abac` (r25), `0x02b5fc` (r25), `0x045da0` (r24) |
| **`0x4e1f` (Pb)** | `0x045d50` (r24), `0x045d8e` (r24), `0x045dce` (r24), `0x1c1270` (r25,r17) |
| `0x0b77` (AC3 sync) | **0 сайти** |
| `0x3000` | 5 сайтів (`0x025d78`, `0x025d80`, `0x02b140`, `0x0a5d44`, `0x10c1c0`) |

**Це прямо суперечить висновку R8** («no IEC61937 sync constant in the firmware»):
R8 шукав літерали в *data/rodata*, а константи **зашиті в код як immediates**. Виправляю
цей висновок тут.

**`0x0b77` як immediate відсутній** → payload не синтезується, а копіюється (узгоджується
з pass-through).

### 2.2 Блок побудови preamble (три копії)

Один і той самий 5-інструкційний блок повторюється тричі: **0x045d4c**, **0x045d8a**, **0x045dca**
(зсуви фаз чергуються 0→2 — змішана ширина, підтверджено):

```
ld/st  r24, r3, 0x016d        ; [r3+0x16d] <- Pa-слот
ori    r24, r0, 0x4e1f        ; r24 = 0x4E1F  (Pb)
ld/st  r5 , r3, 0x0173        ; [r3+0x173]
ld/st  r24, r3, 0x016f        ; [r3+0x16f] <- 0x4E1F  (Pb)
ld/st  r23, r3, 0x0171        ; [r3+0x171]
```

Чотири послідовні 16-бітні поля з кроком 2:

| зсув від r3 | поле |
|---|---|
| `+0x16d` | **Pa = 0xF872** |
| `+0x16f` | **Pb = 0x4E1F** |
| `+0x171` | **burst-info / data-type** |
| `+0x173` | **length code** |

Це **точно структура IEC61937-пreamble** (Pa, Pb, тип, довжина) і вона збігається з тим,
що лежить у DM `0x0A00–0x0A03`: `f872 4e1f 0001 3000`.

### 2.3 Чого НЕ доведено

**Значення r3 не встановлене.** Перевірено: у всьому діапазоні `0x043000–0x04a000`
**немає жодного** звернення до DM-вікна `movhi 0x1c01` (повний перелік таких пар по образу
складається лише з DM `0x1ad0/0x1000/0x1e10/0x1080/0x1bc8/0x26b0/0x5840/0x1a90/0x2678/0x2594/
0x259c/0x2000/0xd0e7`, і жодної — у районі burst-коду).

Тому **я не стверджую, що цей блок саме той, що пише DM `0x0A00`.** Можливості:
(a) r3 передається/завантажується з дескриптора і вказує на DM `0x0A00`;
(b) це writer іншого буфера (наприклад HDMI — у DEC є `Mstar_DTS_Hdmi_Packer`).

Статус: **код побудови IEC61937-preamble ЗНАЙДЕНО (PROVEN); зв'язок із конкретно
DM `0x0A00` — НЕ ВСТАНОВЛЕНИЙ.**

## 3. Caller chain — НЕ ВСТАНОВЛЕНО

Для зворотного трасування потрібен надійний розбір змішаної ширини (16/32 біт) на
ділянках >0x100 байт — блоки 0x045d8a і 0x045dca мають різну фазу при однакових
інструкціях, тобто між ними є 16-бітні інструкції. За вказівкою — branch-target
brute-force не робив. **Першу умову AC3-vs-DTS статично не локалізовано.**

---

## 4. `output_spdifSz` — явно НЕ proven (важливо)

Рядок `Invalid Spdif license:%d, output_spdifSz:%d` має VA `0x02811904`
(file `0x144904`). Перевірено двома способами:

* `ori rN, rN, 0x1904` у всьому образі — **лише 2 входження**, обидва в таблицях даних;
* жодного 32-бітного слова зі значенням `0x02811904` (тобто немає й таблиці вказівників);
* два «майже попадання» перевірено вручну і **відкинуто**:
  * `0x0318f8` — байти `0c 19 04 e7`, сусідній `movhi r3,0x0281` @`0x0318dd` насправді
    утворює `ori r3,r3,0x7d08` (інший рядок);
  * `0x17835a` — середина таблиці даних (`… 35 f7 ff ff 19 04 00 00 …`), а не код.

**Наслідок (прямо як ви вимагали — не підміняю одне іншим):**

```
DTS: output_spdifSz = 0      -> writer skipped        НЕ ДОВЕДЕНО
DTS: output_spdifSz != 0     -> skipped з іншої причини  НЕ ВИКЛЮЧЕНО
```

Єдине твердження, яке я можу захистити: **буфер DM `0x0A00` під DTS не перезаписується
взагалі** (R12, ≥90 с, навіть не обнуляється). Це *сумісне* з `output_spdifSz == 0`,
але **не доводить** його, і тим більше не доводжує, що причина саме в ньому.
**Позначка `output_spdifSz` у R12 як «PROVEN» знімається.**

## 5. PM read — НЕ ВИКОНАНО

`adb` у цьому середовищі відсутній (`command not found`). Пункт перенесено; він лишився
верифікаційним і не блокує основний висновок.

---

## 6. `0x109B` / `0x10A5` — статичні readers не знайдено, записів не робили

За вказівкою — **ніяких DM-write**. Спроба знайти статичні звернення:
перелік `ld/st`, що йдуть після встановлення бази `movhi 0x1c01 + ori 0x1000`,
дав **395 різних пар (rA, imm16)** — евристика надто шумна (сканування обох фаз
підхоплює сміття), ізолювати `0x9B`/`0xA5` не вдалося.

Гіпотеза для перевірки: `0x109B = 0x1000 + 0x9B` і `0x10A5 = 0x1000 + 0xA5` — обидва
виглядають як зсуви від DM-бази `0x1000`, але **жодної інструкції, що достеменно
використовує `0x9B`/`0xA5`, не знайдено**. Статус: **НЕВИЗНАЧЕНО**; контрольований
re-init експеримент наразі **не виправданий**.

## 8. Оновлений ланцюг

### AC3 (підтверджені ланки)
```
ES AC3
 -> DEC "CPU MS12V2 ddp hook/init ok"                       [R11 log]
 -> побудова IEC61937 preamble: Pa=0xF872, Pb=0x4E1F,
    потім data-type і length  -> [r3+0x16d..0x173]          [R13, DEC 0x045d4c/8a/ca]
 -> payload копіюється (0x0B77 не синтезується)             [R13, 0 immediate-сайтів]
 -> DM 0x0A00.. перезаписується безперервно                 [R11/R12 дампи]
 -> SPDIF TX -> AVR locks DD                                [R9]
```

### DTS (підтверджені ланки)
```
ES DTS
 -> DEC "dts m6 hook ok" / "dts m6 init ok"
 -> dts/lbr/xll/transcoder_licensee = 0
       (значення з пам'яті у вікні 0x0001xxxx — точні адреси не підтверджені)
 -> ДЕКОДЕР ПРАЦЮЄ: "dec play !!", cpt/elaplsed ростуть     [R11]
 -> writer preamble/буфера НЕ ПИШЕ: DM 0x0A00 = старий AC3 burst >=90 с  [R12]
 -> тиша
```

**Найцінніше, що дає R13:** код, який AC3-шлях виконує, а DTS-шлях — ні, **локалізовано
як побудову IEC61937-preamble в DEC** (0x045d4c / 0x045d8a / 0x045dca). Саме цей блок —
точка, від якої треба йти назад, коли буде 16-бітний декодер.

## 9. Достовірність

| твердження | статус |
|---|---|
| DEC містить `ori rX, r0, 0xf872` та `ori rX, r0, 0x4e1f` (4 і 4 сайти) | **PROVEN** |
| Блок 0x045d4c/8a/ca пише 4 послідовні 16-бітні поля `+0x16d/16f/171/173` | **PROVEN** |
| Ці 4 поля = Pa/Pb/data-type/length (збіг з DM 0x0A00–0x0A03) | **STRONGLY SUPPORTED** |
| `0x0b77` не зустрічається як immediate (payload копіюється) | **PROVEN** |
| Цей блок пише саме DM `0x0A00` | **НЕ ВСТАНОВЛЕНО** |
| `op 0x35` = store (`sw imm16(rA), rB`) | **STRONGLY SUPPORTED** |
| Формат licensee = `0x02813ae2` (+13 усередину рядка) | **PROVEN** |
| 4 licensee завантажуються з пам'яті вікна `0x0001xxxx` | **SUPPORTED** |
| Точні адреси licensee | **НЕ ВСТАНОВЛЕНО** |

## 10. Що далі (мінімальний набір)

1. **Добудувати 16-бітний op decoder** на двох коротких вікнах: `0x045d40–0x045de0`
   (burst writer) і `0x01e64a–0x01e686` (licensee args). Відповідь на обидва головні
   питання R13 лежить у цих ~150 байтах.
2. **Визначити r3 у блоку 0x045d4c** — це дасть адресу буфера і підтвердить/спростує
   зв'язок із DM `0x0A00`.
3. **З'ясувати вікно `0x0001xxxx`** (PM? другий DM-банк? периферія?) — від цього залежить,
   чи переводяться адреси licensee в DM-адреси, доступні через `read_dsp_sram_type`.
4. PM read — лише після появи доступу до пристрою.
