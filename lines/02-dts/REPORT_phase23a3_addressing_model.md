# R23-A.3 — Provenance / addressing model of `0x0F45` / `0x0F4B` / `0x0F7B`

**Дата:** 2026-09-08, 15:27–15:45 EEST
**Пристрій:** Thundeal TD98 Pro / C50A (MStar MT5889 + AEON DSP)
**Режим:** static only. Жодних runtime-захоплень, патчів, змін налаштувань, EDID/топології.
**Головне питання:** чи є `0x0F45/0x0F4B/0x0F7B` справжніми DSP-visible полями, чи лише клітинками, які `/proc/utopia_mdb/audio` читає через окремий host/kernel механізм?

---

## Підсумок (коротка відповідь)

> **UNRESOLVED: `0x0Fxx` provenance / DSP visibility NOT PROVEN.**
>
> Доведено: ці адреси є **16-розрядними індексами клітинок регіону «DM»**, які читаються **host/kernel debug-шляхом** (proc → `utpa2k.ko` → `HAL_MAD2_Read_DSP_sram` → `_HAL_MAD2_DBG_CMD_Read_DSP_sram` — debug-команда до ядра MAD2).
>
> **Не доведено:** що ці клітинки адресуються DSP-кодом як пам'ять (через base + displacement), і, відповідно, не знайдено жодного writer/reader.

Відповідно до правила Evidence, жодних висновків про роль цих полів у DTS-виводі **не робиться**.

## Крок 1 — Контрольний приклад R8: відтворено і перевірено побайтово

### 1.1 Ланцюг (підтверджено незалежним читанням образу)

| Елемент | Значення |
|---|---|
| Образ | `r2img/mst_snd_r2_MS12V22.bin` |
| DSP-адреса завантаження | `0x016F84` |
| Матеріалізація бази, крок 1 | `0x016EC6` → BE слово `0xC1800021` → `movhi r12, 0x0021` |
| Матеріалізація бази, крок 2 | `0x016ECA` → BE слово `0xFD8CA000` → `ori r12, r12, 0xA000` |
| Базовий регістр | `r12` = **0x21A000** (SHM window) |
| Інструкція | `0x016F84` → BE слово `0xEEEC00FA` → `LD r23, 0xFA(r12)` |
| Effective address | `0x21A000 + 0xFA` = **0x21A0FA** |
| Відповідність полю хоста | DSP `+0xFA` ↔ ARM SHM `+0xF8` (param `0x6E`, AC3/DTS discriminator), зсув −2, перевірено на 12/12 полях |

### 1.2 Критичне технічне виправлення

**Інструкції в DSP-образі — BIG-ENDIAN.** Immediate розташоване у **молодших 16 бітах BE-слова**:

```
0x016F84: байти EE EC 00 FA  →  BE 0xEEEC00FA  →  imm16 = 0x00FA   ✓
0x016EC6: байти C1 80 00 21  →  BE 0xC1800021  →  imm16 = 0x0021   ✓
0x016ECA: байти FD 8C A0 00  →  BE 0xFD8CA000  →  imm16 = 0xA000   ✓
```

Усі три immediate збіглися точно — гіпотеза endianness підтверджена незалежно на трьох точках.

**Наслідок:** попереднє static-сканування (R23-A.2) виконувалося з little-endian інтерпретацією і тому перевіряло **не те поле** (старші 16 бітів = opcode+регістри замість immediate). Це повністю пояснює тодішній негативний результат. Методика була правильною,解码 — ні.

### 1.3 Чому R8 **не є** шаблоном для DM-клітинок

R8 встановлює ланцюг `base → load → поле`, але:
- `+0xFA` — це поле **SHM** (host-shared memory), а не DM;
- відповідність «адреса DSP ↔ значення, видиме з хоста» встановлена в R8 **не арифметикою адрес**, а *field-value echo* (ARM пише відомі значення параметрів 0x68/0x69/0x6b/0x6c/0x6d/0x6e…, DSP їх читає);
- жодна ланка R8 **не пов'язує** адресу DSP із клітинкою, яку повертає `/proc/utopia_mdb/audio`.

Тобто R8 доводить життєздатність методу там, де є база, але не переноситься на `0x0F45`.

## Крок 2 — Чи належить `0x0Fxx` тому самому address space?

### 2.1 Спільного вікна для `+0xFA` і `0x0F45` не існує

| Ознака | SHM (R8) | DM (`/proc/utopia_mdb/audio`) |
|---|---|---|
| База | `0x21A000` (доведена) | невідома / не доведена |
| Діапазон зміщень | малі: `0x8E`…`0x12E` | повний 16-бітний: `0x0000`–`0xFFFF` |
| Ширина даних | 16-бітні значення, byte-offset | **24-бітні** значення, індекс клітинки |
| Адресація | byte-addressed (`+0xFA`) | **cell-indexed** |

Різниця принципова: `0x0F45` лежить поза діапазоном зміщень SHM-вікна і має іншу розмірність даних. Припущення

```
cell 0x0F45  ==  DSP base + 0xF45
```

**не підтверджено і наразі хибне для єдиного доведеного вікна (SHM).**

### 2.2 Реальні load/store до вікна `0x0Fxx`: не знайдено

Повторно, з **правильним BE-декодуванням**, виконано цільовий пошук immediate `0x0F45` / `0x0F4B` / `0x0F7B` на 2-байтовому вирівнюванні:

```
0x0F45: 99 збігів
0x0F4B: 88 збігів
0x0F7B: 56 збігів
```

**Жоден збіг не має матеріалізованої бази поблизу** (немає `movhi/ori`-послідовності, яка формувала б вікно, в межах якого цей immediate був би зміщенням). Контекст збігів не містить ні спільного базового регістра, ні серії звернень до сусідніх зміщень.

За правилом Evidence це **displacement coincidence**, яке явно **не є** доказом writer/reader. Окремого base/window для low-DM region **не виявлено**.

### 2.3 Host/kernel шлях, який створює ці дані — ВСТАНОВЛЕНО

Це ключовий результат кроку 2.4.

**Формат виводу (рядок із дампу) належить ядру:**

```
utpa2k.ko:  "DM[0x%04x] = 0x%06lx "
```

- маркування регіону — **«DM»** (власне маркування виробника);
- `%04x` — адреса є **16-розрядним індексом** (0x0000–0xFFFF);
- `%06lx` — значення **24-бітне**.

Отже `addr=0x0F45` — це **індекс клітинки в DM**, а не байтова адреса у плоскому 32-бітному просторі.

**Ланцюг читання:**

```
/proc/utopia_mdb/audio
  "read_dsp_sram_type=<type> addr=<addr> len=<len>"
        ↓
utpa2k.ko  — proc-обробник, форматує "DM[0x%04x] = 0x%06lx"
        ↓
libutopia.so: HAL_MAD2_Read_DSP_sram
        ↓
libutopia.so: _HAL_MAD2_DBG_CMD_Read_DSP_sram     ← DBG CMD (debug-команда до DSP)
        ↓
ядро MAD2 (MAD2_SetDspIDMA / dsp_dbg_cmd) повертає вміст своєї SRAM
```

Наявність **`_HAL_MAD2_DBG_CMD_Read_DSP_sram`** і `dsp_dbg_cmd` вирішальна: читання DM — це **host-ініційована debug-команда**, яку DSP виконує сервісною процедурою і повертає результат. Це **не** свідчить, що основний DSP-код звертається до цих клітинок як до пам'яті.

**Висновок кроку 2.4: так** — `/proc/utopia_mdb/audio` читає DM через окремий host/kernel (debug) механізм, незалежний від адресації в коді DSP.

## Крок 3 — Статус трасування `0x0F45` / `0x0F4B` / `0x0F7B`

Умова для трасування (`known base → actual load/store → effective address in 0x0Fxx`) **не виконана**: база невідома, вікно не доведене. Тому writer/reader **не трасується** (і, згідно з наказом, brute-force opcode search не застосовувався).

```
UNRESOLVED:
  0x0Fxx provenance / DSP visibility NOT PROVEN
```

### Що це означає для попередніх результатів

Раніше встановлені runtime-факти залишаються чинними **як спостереження** і не залежать від цього висновку:

| Адреса | IDLE | AC3 | DTS |
|---|---|---|---|
| `0x0F45` | `0x000008` | `0x000008` | `0x000000` |
| `0x0F4B` | `0x2233C0` | `0xAA33C0` | `0x2233C0` |
| `0x0F7B` | `0x2233C0` | `0xAA33C0` | `0x2233C0` |

Але коректна назва для них тепер — не «поля SHM» і не «DSP control fields», а:

> **reproducible AC3-vs-DTS differential value in a DM cell of unproven DSP visibility**

Жодного семантичного ярлика («codec ID», «license flag», «output flag») не надається.

## Evidence-статус

**VERIFIED**

- Інструкції DSP-образа — big-endian; immediate — у молодших 16 бітах (підтверджено на 3 незалежних точках ланцюга R8).
- R8-ланцюг відтворено побайтово: base `0x21A000` (r12), `LD r23,0xFA(r12)`, EA `0x21A0FA`, поле ARM SHM `+0xF8`.
- Формат дампу `DM[0x%04x] = 0x%06lx` належить `utpa2k.ko`: адреса — 16-бітний індекс клітинки, значення — 24-бітне.
- Шлях читання: proc → `utpa2k.ko` → `HAL_MAD2_Read_DSP_sram` → `_HAL_MAD2_DBG_CMD_Read_DSP_sram` (debug-команда до MAD2).
- SHM-вікно R8 (`0x21A000`, зміщення ≤ `0x12E`) **не містить** `0x0F45`; іншої доведеної бази для `0x0Fxx` немає.

**STRONG INFERENCE**

- DM, найімовірніше, є окремою (не byte-addressable у плоскому просторі) data-пам'яттю DSP, доступ з хоста до якої можливий лише сервісно/debug-шляхом. Аргументи: 24-бітна ширина слова, 16-бітний індекс, наявність DBG CMD-інтерфейсу, відсутність будь-якої матеріалізованої бази для цього діапазону.

**UNRESOLVED**

- **Хто записує `0x0F45` / `0x0F4B` / `0x0F7B` — невідомо.**
- **Хто читає ці клітинки — невідомо.**
- Чи адресуються вони DSP-кодом узагалі — невідомо.
- Чи існує ланцюг `AC3/DTS identification → write → read → SDO/IEC61937/DTS packer decision` — невідомо.
- Причина відмови DTS — не встановлена.

## Що потрібно, щоб зрушити з місця (без brute-force)

1. **Отримати карту пам'яті MAD2** (де, якщо взагалі, DM відображається у просторі інструкцій) — з документації або з таблиць завантаження; без цього «base» не існує в принципі.
2. **Визначити семантику параметра `type`** у `read_dsp_sram_type=<type>`: що саме означає `type=1` (наш випадок) і які ще типи існують. Це звузить регіон до конкретного банку/ядра.
3. **Зіставити індекс DM із внутрішнім простором DSP** через код сервісної debug-процедури: знайти в образі обробник DBG CMD для читання SRAM — він і є тим місцем, де індекс `0x0F45` перетворюється на реальну адресу. Це єдиний достовірний місток між «індексом дампу» і «адресою DSP».
4. Лише після появи бази/містка — трасувати writer/reader за правилом `actual instruction → actual base/register → actual EA → matching runtime-visible cell`.
