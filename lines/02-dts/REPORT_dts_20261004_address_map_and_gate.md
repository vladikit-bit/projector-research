## 2. ✅ КОДУВАННЯ ГІЛОК ВИВЕДЕНО З КОРПУСУ

32-бітне слово читається **big-endian** з байтів у порядку файлу.

```
rel_simm = (word >> 3) & 0x1FFF     підписаний 13-бітовий
target   = addr + rel_simm
```

**Перевірка: 10 544 / 10 544 гілок сходяться.** Не 10 544 з 10 544 «приблизно» —
точність.

### Таблиця умовних кодів (біти 0..2)

| код | мнемоніка | семантика |
|---|---|---|
| 0 | `bles` / `blesi` | ≤ |
| 1 | `ble` / `bleui` | ≤ |
| 2 | `beq` / `beqi` | == |
| **3** | **`bf`** | **за прапорцем умов (без порівняння)** |
| 4 | `bgts` / `bgtsi` | |
| 5 | `bgt` / `bgtui` | > |
| 6 | `bne` / `bnei` | != |
| 7 | `b111` / `b111i` | |

**Важливо:** 3-байтового безумовного переходу в ISA **немає**. Усі 3-байтові
інструкції — АЛУ / завантаження / збереження / умовна гілка.

## 3. 🔴 «SND-гейт 0xB6CB5» — ФАНТОМ, ВІДКЛИКАНО

`0xB6CB5` **не є початком інструкції** в DEC-лістингу. Воно лежить усередині:

```
0461cb4 → 0461b4  3  bn.addi r16,r13,0x78     байти 1e0d78
                                               ^^^^^
                                      0xB6CB5 = другий байт
```

Записана раніше інструкція `blesi r11+0x54,0` — **результат дизасемблювання зі
зсувом на байт**. Це той самий клас помилки, що й дві раніше відкликані межі
функцій SND (див. `FORENSIC_dts_listing_purity_20260930.md`, Result 2).

> **Правило, яке тепер діє:** адреса з пам'яті не є доказом наявності інструкції.
> Перш ніж аналізувати — перевірити, чи є адреса в `dec33_realcode.txt`.

## 5. ✅ ФУНКЦІЯ-ГЕЙТ ДЕКОДОВАНО (0x4618E … 0x4629x)

```asm
04618e  addi r1,r1,-0x20          ; пролог, 32 байти стеку
0461a1  lwz  r23,0x28(r3)         ; r23 = [+0x28]
0461a4  mov  r10,r3
0461a6  movi r14,0
0461a8  beqi r23,0x1,0x461c4      ; === САЙТ 1 ===
0461ab  sw_0 0xf0(r10),r14       ; вихід: [+0xF0] = 0
   ...відновлення регістрів...
0461bf  addi r1,r1,0x20
0461c2  jr  r9                    ; return
   ---- рука == 1 ----
0461c4  lwz  r14,0x38(r3)         ; r14 = [+0x38]   <-- ЛІЧИЛЬНИК
0461c7  lwz  r3,0xf8(r3)          ; буфер A
0461cb  slli r11,r14,0x2          ; stride = [+0x38] * 4
0461d2  jal  memset(A, 0, stride)
0461de  jal  memset(буфер B, 0, stride)
0461e2  lwz  r25,0x30(r10)        ; [+0x30]
0461e5  lhz  r24,0x16c(r10)       ; [+0x16C]
0461eb  ori r12,r0,0x12           ; фазовий зсув = 18 біт
0461f7  bnei r24,0x0,0x462a0      ; єдиний обхід циклу
0461fd  ble  r14,r16,0x46259      ; поріг циклу
   ---- цикл ----
046201  lwz  r5,0xf8(r10) / lwz r3,0xfc(r10)
046210  jal  0x64369
046232  sll  r25,r25,r12 / sra r25,r25,r12     ; масштабування через 18
046238  sw   0x0(r24),r25
04624b  bgt  r14,r13,0x4620a      ; наступна ітерація
   ---- після циклу ----
046259  lwz  r23,0x2c(r10)        ; [+0x2C]
04625c  bnei r23,0x1,0x461ab      ; === САЙТ 2 ===
046260  lwz  r23,0x30(r10)
046266  lhz  r23,0x16c(r10)
04627b  ori  r25,r0,0x7ffe        ; константа A
046285  ori  r25,r0,0x8001        ; константа B
```

**Що це за функція:** обнулення пари буферів і копіювання з масштабуванням
(апроксимація ділення на 2^18 через sll+sra), далі — запис маркерних констант
`0x7FFE` / `0x8001` у два місця.

**Гейт — дві умови на дані, не на код:**

| умова | адреса | наслідок невиконання |
|---|---|---|
| `[+0x28] == 1` | 0x461A8 | вихід, `[+0xF0] = 0` |
| `[+0x2C] == 1` | 0x4625C | вихід у 0x461AB |

Розмір роботи задає `[+0x38]` — помножений на 4 стає довжиною memset.
Це **та сама** `[0x38] == 0x400`, про яку йшлося раніше.

**Чому попередні патчі дали нуль:** вони правили *код* на шляхах, які блокуються
*даними* ще до входу. Тут код живий — невиконані саме `[+0x28]` / `[+0x2C]`.

## 6. ВІДКРИТЕ — ЩО САМЕ ЛАМАЄ ГЕЙТ

1. **Немає прямих викликів функції.** Жодна гілка в корпусі не веде на `0x4618E`
   або `0x461A1`. Функція досягається **непрямим диспетчером** — узгоджується з
   наявністю блоків `cmov_0/cmov_1` (jump table) у цьому ж лістингу.
   → наступний крок: розібрати jump table, яка саме гілка приходить у цю функцію
   для DTS і для AC-3.

2. **382 писаці на `+0x28`.** Зсув сам по собі нічого не визначає — потрібен
   dataflow по базовому регістру. Наивне зіставлення за зсувом дає сміття.

3. **Значення `[+0x28]`, `[+0x2C]`, `[+0x38]` не спостережені.** За попередніми
   нотатками їх не видно з хоста. Якщо станеться отримати хоча б одне — ми знатимемо,
   яку саме умову ламати.

## 7. ЩО ЦЕ ДАЄ ДЛЯ ПАТЧА

Карта адрес тепер доведена, кодування гілок доведене, обидва сайти — реальний код із
відомою поведінкою. **Єдине, чого бракує — спосіб зробити умову гілку безумовною.**

Три бачені варіанти, усі з реальною перевіркою:

| варіант | ідея | ризик |
|---|---|---|
| A | `bf` (код 3) замість `beqi` — гілка за прапорцем | невідомо, хто ставить прапорець після `lwz`/`movi` |
| B | знайти `r23`, яке гарантовано не 1, і порівняти з ним | потребує імпліцитного значення — є в інструкціях |
| C | патчити **виробника** `[+0x28]`, а не гілку | правильніша мета, але треба знайти jump table |

**C — найправильніша мета**: ламати умови марно, якщо рушій ніколи не ставить
`1` у `[+0x28]` для DTS.

# 🔴 ВИПРАВЛЕННЯ 2026-10-04 (пізно ввечері) — три перевищення в цьому ж звіті

Користувач сказав «подумай ще раз критично, а не тупо приймай усе». Пере-перевірка
знайшла три місця, де я написав більше, ніж довів.

## Виправлення 1 — кодування гілок стосувалось ЛИШЕ 4-байтових

Я написав «10 544 / 10 544» без застереження. Але мій скрипт мав `if ln!=4: continue`.

**3-байтові гілки (bn.*) мають ІНШЕ кодування** — перевірено: формула 4-байтових дає
**0/8000** збігів. Справжня:

```
rel = (слово >> 2) & 0xFF      підписаний 8-бітовий, діапазон ±127
умова = біти 0..1              0 = beqi, 2 = bnei
```

Перевірка: **10 793 / 10 983**, і всі 190 «невдач» — це `bn.cmovi`, інша інструкція,
яку мій regex випадково зловив. Для самих гілок — ідеально.

**Наслідок:** сайт 1 (0x461A8) — 3-байтовий, і його кодування тепер підтверджене
окремо: `22e470` → rel=0x1C → 0x461A8+0x1C = 0x461C4 ✓.

**Але:** у 3-байтових гілках існують лише умови 0 (beqi, 5033 прикладів) і 2 (bnei, 2948).
Кодів 1 і 3 у корпусі немає — **зробити 3-байтову гілку безумовною зміною умови неможливо.**

## Виправлення 2 — «0xB6CB5 фантом»: висновок стоїть, підстава була хибною

Я перевіряв **DEC**-лістинг, а твердження в пам'яті стосувалось **SND**. У SND-фільтрі
досяжності `0xB6CB4/5` теж відсутні — тож висновок («не валідна ціль патча») витримав,
але тепер з правильної підстави.

## Виправлення 3 — «прямих викликів немає» БУЛО ХИБНИМ

Мій пошук застосовував до `bg.jal` формулу умовної гілки. **`jal` — відносний, з іншим
зсувом:** `ціль = адреса + ((слово>>1) & 0x1FFFFF)` — перевірено **6000/6000**.

З правильним кодуванням:

```
0x041289:  bg.jal 0x0004618e     ← ЄДИНИЙ прямий виклик функції-гейту
```

І `0x4121E` (старий сайт H3) лежить **в тій самій функції**, що й цей виклик.

## Що показує викликач (0x41200..0x41295)

```asm
04120b  beqi r24,0x1,0x411db        ; [r23+0xB94]
041213  lwz  r12,-0x5edc(r11)       ; r11 = r3 + 0x10000
04121e  beqi r23,0x1,0x41275        ; <<< H3: [r11+0x4EE4] == 1
041221  sw_0 0x4dbc(r11),r0         ; [r11+0x4DBC] = 0
   --- ціль H3 (0x41275) ---
041275  movhi r23,0x1 / ori r23,r23,0x4ccc   ; r23 = 0x14CCC
04127d  lwz  r4,-0x5ef8(r11)
041283  jal  0x45fd1
041289  jal  0x4618e                ; <<< ВИКЛИК ГЕЙТУ
04128d  bnei r12,0x1,0x411c9
```

**Структура:** перед викликом гейту обчислюється вказівник `r3 = … + 0x14CCC`.
Гейт далі читає `+0x28 / +0x2C / +0x38` **від цього зсуву** — тобто фактичні
адреси `база+0x14CF4`, `база+0x14CF8`, `база+0x14D04`.

**Наступна ціль:** хто пише в `+0x28` **відносно цього конкретного базового регістра** —
тепер пошук звужено з «382 писаці» до «писаці з тим самим базовим регістром».
