# R3 — `mi_getCodecType` / `MI_AUDIO_GetHandle` Differential Trace

**Target**: Thundeal TD98 Pro / C50A — MediaTek MT5889, Android 11, kernel 4.19.116
**Subject**: `E audio_hw_primary: mi_getCodecType: MI_AUDIO_GetAttr failed, ret=0x3` and
`E audio_hw_primary: mi_getCodecType: MI_AUDIO_GetHandle failed!!! ret = 9`
**Question**: Are these DTS-specific, and do they show DTS failing at codec/DSP handle acquisition?
**Verdict**: **R3-B** — the errors are **neither DTS-specific nor on the playback path**.

## 1. VERDICT — R3-B

> **`mi_getCodecType` is not part of the playback path at all.**
> It is a *diagnostic dump helper* invoked 4× by `dumpsys media.audio_flinger`, probing the
> device names `DTV`, `HDMI`, `OMX`, `AudioHAL`. The two error messages are the **normal,
> expected** outcome for the 3 of those 4 names that have no live MI_AUDIO decoder handle.
>
> They occur **identically at idle with no playback running**, and occur **zero times during
> playback** for both AC3 and DTS.
>
> Consequently the R3 working hypothesis — *"DTS may fail during codec/DSP handle acquisition
> before the SDO/IEC61937 transmit stage"* — is **REFUTED**. DTS acquires its decoder handle and
> opens the raw output exactly like AC3.

The user's caution is vindicated: **`MI_AUDIO_GetHandle ret = 9` must NOT be treated as evidence
that the DTS SDO/IEC61937 packer is broken.** It is a red herring generated by the dump command.

### 2.5 Implementation layer of `MI_AUDIO_*`

All four symbols are **imports** in the HAL (`shndx = 0`) and are **defined in `libmi3.so`**:

| Symbol | HAL PLT thunk | libmi3.so definition | size | ioctl |
|---|---|---|---|---|
| `MI_AUDIO_Open`      | — | **0x62695** | 492 | (separate) |
| `MI_AUDIO_Start`     | — | **0x629ad** | 196 | (separate) |
| `MI_AUDIO_GetAttr`   | **0x3df70** | **0x635c1** | 244 | **`0xC0181013`** |
| `MI_AUDIO_GetHandle` | **0x3df20** | **0x6388d** | 348 | **`0xC0441015`** (`MI_DEV_IOC_AUDIO_GET_HANDLE`) |

Verified in `libmi3.so`:

```
0x635d8: cmp.w   r7, #-1 ; ble #0x6365c     ; GetAttr: fd < 0 -> internal error return
0x6361e: movw    r1, #0x1013
0x63626: movt    r1, #0xc018                ; ioctl cmd = 0xC0181013
0x6362a: blx     #0xaffe0                   ; ioctl()
```

`libutopia.so`, `libalsautils.so`, `libaudioparser.so` export **none** of these.

**Where 9 and 3 come from.** `libmi3.so`'s own pre-checks return only **4** (invalid MI device fd)
and **8** (bad arguments) for `MI_AUDIO_GetHandle`, and **4** for `MI_AUDIO_GetAttr`. Neither
**9** nor **0x3** is in that set, so both values are the **kernel driver's response to the ioctl**,
i.e. produced below libmi3 (in `mik.ko` / `utpa2k.ko`). This is corroborated at runtime — see §3.3.

## 4. THE AC3-vs-DTS DIVERGENCE POINT (playback path)

Both formats traverse the **identical** sequence. The **only** differences are the format
constant and the vendor codec ID:

| Stage | AC3 | DTS |
|---|---|---|
| `adev_open_output_stream` | `handle:45 dev:speaker fmt/chn/sr 0x09000000/2/48000, flag 0x00000011` | `handle:53 dev:speaker fmt/chn/sr 0x0b000000/2/48000, flag 0x00000011` |
| offload open | `... with offload fmt/chn/sr 150994944/2/48000` | `... with offload fmt/chn/sr 184549376/2/48000` |
| parser | `parser open ok.` | `parser open ok.` |
| `mi_decoder_open` | **`format 5` got decoder handle `0x19000000`** | **`format 9` got decoder handle `0x19000000`** |
| `mi_common_raw_open` | `handle 45, open raw output for device[speaker]` | `handle 53, open raw output for device[speaker]` |
| `out_write` | `handle=45, ... enter PLAY state` | `handle=53, ... enter PLAY state` |
| AudioPatch | `id(106) ... format(0x09000000), mix hw_module(10) handle(45)` | `id(110) ... format(0x0b000000), mix hw_module(10) handle(53)` |
| Kodi sink | `AudioTrack (IEC)` selected | `AudioTrack (IEC)` selected |

**Both obtain the same decoder handle `0x19000000`.** Both open raw output. Both reach PLAY.
Neither logs a single `E audio_hw_primary` line.

**Upstream data delivery is alive and correct for both** — the audio parser is emitting
well-formed frames throughout:

```
AC3: 259 × Parser_Write ; "Out f(132) current frame size[1536] sr(48000)"   <- 1536 B = AC3 5.1 @48k
DTS: 360 × Parser_Write ; "Out f(732) current frame size[2012] sr(48000)"   <- 2012 B = DTS 5.1 @48k
```

**HAL `Settings:` block is byte-identical** AC3 vs DTS (`diff` → no output):

```
sink device: 0x2 / DAP: mcu 0 / downmix_mode: 0 / Dolby version: 10 / Dolby bypass: 0
DTS DRC scale: 0
hdmi arc mode: ui(auto), current(auto)      hdmi arc type: ui(not-specified), current(not-specified)
hdmi tx  mode: ui(auto), current(auto)      hdmi tx  type: ui(not-specified), current(not-specified)
spdif    mode: ui(auto), current(auto)      spdif    type: ui(not-specified), current(not-specified)
spdif delay: 0
```

The only error anywhere in the DTS playback window is
`E/AudioFlinger(339): Failed to add event callback` — and it appears **once in AC3 as well**,
at the same point (stream open). It is benign and format-independent.

### Divergence point, stated precisely

```
                      AC3                              DTS
  Kodi IEC packer  --> AudioTrack(IEC)             --> AudioTrack(IEC)        [identical]
  AudioFlinger     --> offload stream              --> offload stream         [identical]
  HAL format       ->  0x09000000                  ->  0x0b000000             <-- DIFFERS
  mi_decoder_open  ->  codec id 5, handle 0x19000000   codec id 9, handle 0x19000000
                                                                              <-- DIFFERS (id only)
  mi_common_raw_open / out_write PLAY                                          [identical]
  ------------------------------------------------------------------------------------
  >>> everything measured so far is successful for BOTH <<<
  >>> the fault therefore lies DOWNSTREAM of raw-output open: the SDO / IEC61937
      transmit stage (or the SPDIF sink's decode of the DTS burst), not in
      handle acquisition, decoder open, or parser output. <<<
```

## 5. What R3 does and does not establish

**Established**

1. `mi_getCodecType` (0x0328d0) is a dump-only helper, called 4× from the ops-table dispatcher
   0x0322d4 with names `DTV` / `HDMI` / `OMX` / `AudioHAL`.
2. `ret = 9` and `ret = 0x3` are **kernel ioctl rejections** below `libmi3.so`
   (`MI_DEV_IOC_AUDIO_GET_HANDLE` / `0xC0181013`), not HAL logic errors.
3. They are **format-independent**: identical at idle, under AC3, and under DTS.
4. The playback path is **error-free for both AC3 and DTS** up to and including `out_write` PLAY
   and the raw-output open.
5. DTS **successfully** acquires decoder handle `0x19000000` — the same handle AC3 gets.

**Not established (and explicitly not claimed)**

* R3 does **not** prove the SDO/IEC61937 packer is broken. It only **eliminates** handle
  acquisition as the failure point. The remaining candidate region is the transmit stage.
* The 23-entry MI_AUDIO codec-type enum in the `tbh` switch at 0x0329d2 was **not** decoded to
  names. This is documentation-only and does not affect the verdict; the runtime values that
  matter (`NONE`, `XPCM`, `AC3`, `DTS`) are already observed empirically in the dumpsys output.
* Kernel-side behaviour (inside `mik.ko` / `utpa2k.ko`) was not observable — the DTS and AC3
  `dmesg` windows contain no SDO/IEC/audio-path messages, only unrelated SELinux `avc` denials,
  VDEC activity, and benign `MI3_DEBUG` lines from a different PID.

## 6. Consequence for the investigation

The R3 hypothesis is closed. The search space narrows to everything **after** `mi_common_raw_open`:

1. `mi_common_raw_write` (0x031164) and its `MI_AUDIO_*` write path into the DSP.
2. The MAD R2 / SDO output stage — how a DTS burst is framed onto SPDIF vs an AC3 burst.
3. The DTS license/decoder-support masks in `g_AudioVars2` (`0x440` / `0x444` / `0x4d0` / `0x4d8`
   / `0x582`) as they apply to the **transmit** decision rather than the open decision.

Note the corroborating signal already visible in the dump output:

```
Supported ARC capability: dd:0, ddp:0(atmos:0), dts:0, aac:0, mat-truhd:0(Byte3:0), dtshd:0,
```

— present and identical in all three phases.
