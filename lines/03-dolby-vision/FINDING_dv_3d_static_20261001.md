## 1. DV: бібліотека декодера

| Параметр | Значення |
|---|---|
| Жива копія | `/vendor/lib/libOMX.MStar.so` |
| Друга копія | `/mnt/vendor/tvservice/glibc/libOMX.MStar.so` |
| Споживач | `media.codec` PID 496 (`MSTAR_VDEC_API 496` у логу) |
| Розмір / архітектура | 577 128 Б, ARM32 Thumb-2, 1047 експортованих FUNC |

Друга копія — в телекорпоративному каталозі; **розбиралась правильна** (та, що в
`/vendor/lib`, її тримає `media.codec`).

### 1.1 `MsVdecGetLumaBitDepth` @0x330C4 — розбір байт-у-байт

Функція 28 байт, Thumb:

```asm
ldr    r1, [pc, #0x14]     ; покажчик через GOT
ldrb   r0, [r0, #8]         ; enum кольорового формату, ctx+8
movw   r2, #0x34B0           ; крок таблиці
movt   r2, #0
smlabb r0, r0, r2, r1        ; r0 = база + enum * 0x34B0
movw   r1, #0x3454           ; офсет бітності в записі
ldrb   r0, [r0, r1]          ; <- значення бітності
bx     lr
```

**Таблиця кольорових форматів — масив структур по 0x34B0 байт, бітність на офсеті 0x3454.**

### 1.2 Сусіднє сім'я геттерів (усі по 28 байт)

| Адреса | Символ |
|---|---|
| 0x33005 | `MsVdecGetSecureHandleSize` |
| 0x33021 | `MsVdecGetDrmStreamId` |
| 0x3303D | `MsVdecGetStreamUniqueID` |
| 0x330C5 | `MsVdecGetLumaBitDepth` |
| 0x330E1 | `MsVdecGetHDRType` |
| 0x330FD | `MsVdecGetEsAddr` |

### 1.3 Машинерія форматів у бібліотеці

`ConvertYV12ToHVDTile`, `I420ToNV12`, `ConvertI420ToNV12`,
`MsVdec_DetileYUV420`, `MsVdec_DetileYUV_Neon`, `MsVdec_BlankCropAreaYV12`,
`MsVdec_FrameSizeGetByColorFormat`, `MsVdecConvertCodecTypeToColorFormat` @0x35261
(таблиця з 19 записів {тип кодека, колірний формат}, при невідомому типі
повертає запис 0).

Рядки-маркери шляхів:
```
'YV12 to MSTTILE VideoWidth %d VideoHeight %d'
'SW render with DIP-MFDEC support, change color format to NV12'
'GPU-MFDEC enable but didn't use AndroidNativeBuffer, change color format to YV12'
```

### 1.4 Суперечність у рантаймі (з логу декодера)

```
colorFormat=1  bYV12=1  bitdepth=10
luma_pitch=3840  chroma_pitch=1920  width=3840  height=2160
```

`luma_pitch == width` → **1 байт на піксель, тобто фактично 8 біт**, при заявлених 10.

### 1.5 Чому я НЕ раджу патчити це зараз

Якщо буфер поверхні 8-бітний, то `luma_pitch = width` — це **правильна** поведінка,
і справжня помилка в тому, що споживач читає 8-бітний буфер як 10-бітний. Правка
таблиці бітностей тоді нічого не виправить, а зламає нормальний шлях для SDR.

Якір, який вказує на справжнє місце збою, — не внутрішній, а з Android-шару:
```
E/ACodec: [MS.DOLBY_VISION.DVHE.ST.Decoder] setPortMode on output to
          DynamicANWBuffer failed w/ err -1010
E/OMXNodeInstance: BadPortIndex / UnsupportedIndex
```
Тобто ламається **переговори буфера**, і DV-декодер їх не проходить, а звичайний
HEVC проходить (тому без DV картинка правильна).

### 1.6 Технічна перешкода в розкритті таблиці

База таблиці лежить через GOT: літерал `0x330DC` = `0x39850`, далі `add r1,pc` →
`0x6C920`. Щоб прочитати значення, треба застосувати релокації:

- `.rel.dyn` має формат **`ANDROID_REL` з entsize=1** (923 записи по 1 байту) —
  `readelf -r` його **не парсить** (показав лише 794 записи з `.rel.plt`).
- `.relr.dyn` я розгорнув сам: 82 релокації, діапазон 0x6C5A0…0x329300 —
  **GOT (0x6C8DC…0x6CA9C) туди не входить**.
- Читання `/proc/496/mem` для GOT заблоковане (повертає нулі).

Потрібно або реалізувати розбір packed `ANDROID_REL`, або інший шлях.

## 2. 3D: гейт — це відповідь вендорного HIDL-сервісу

Ланцюг `isSupport3D()` (встановлено раніше, підтверджую тут повністю):

```
AdvanceVideoFragment.isSupport3D()            classes7.dex 0x12776C
  → MktTvAVModeBase.getVideoInfoValue(8)
  → TVNative.getVideoInfoValue_1native         @0x47BA1 (140 Б)
  → a_mtktvapi_videoinfo_get_value             (UND у JNI)
  → vendor::mediatek::api::mtktvapi::V1_0::2BpHwMtkTvApi::
      a_hidl_a_mtktvapi_videoinfo_get_value    @0x12A569 (140 Б)
  → MediaTek TV HIDL-сервіс
```

**Отже здатність 3D визначається не ядром і не PQ, а окремим вендорним сервісом
MediaTek TV через HIDL.** Ось чому її не змінює ні меню, ні `settings`, ні жодна
команда mdb.

### 2.1 Ключ конфігурації

| Де шукав | Результат |
|---|---|
| `TvSettingsPlus.apk` classes.dex рядок 13000 | `g_video__vid_3d_item` **є** |
| `TvServices.apk` | немає |
| Усі `.so` у `/vendor/lib`, `/vendor/lib64`, `/system/lib`, `/system/lib64` | **немає** |
| Усі виконувані в `/vendor/bin`, `/system/bin`, `/odm/bin` | **немає** |

Тобто назва ключа живе тільки в застосунку; у вендорних бінарниках її немає —
або сховище порожнє (ми це вже встановлювали), або сервіс називає її інакше.

### 2.2 Що це означає для розблокування 3D

Потрібно змінити те, що **повертає HIDL-сервіс**. Це:
- або патч бінарника TV-сервісу (ще не знайдено, який саме — наступний крок);
- або патч `isSupport3D` в `classes7.dex`, щоб він повертав 1 — але тоді запис
3D піде в `g_*`-сховище, яке порожнє, тобто ефекту не буде.

**Висновок: 3D на цій збірці не розблоковується налаштуванням.** Це вже не
питання PQ і не питання меню.

## 4. ФІНАЛЬНА ТАБЛИЦЯ (2026-10-01, після серії тестів)

Один і той самий файл `One Piece (2023) WEB-DL 2160p **Dolby Vision Profile 8**`
(Hybrid — базовий шар HDR10 + RPU).

| Шлях відтворення | Декодер | Драйвер | Картинка |
|---|---|---|---|
| SDR-файл | `OMX.MS.HEVC.Decoder` | `DolbyVision 0` | ✅ правильно (користувач) |
| **DV P8 у VLC** (VLC ігнорує шар DV) | `OMX.MS.HEVC.Decoder` | `DolbyVision 0`, UHD 1 | ✅ картинка нормальна — **але DV не грався взагалі**, це не доказ роботи HDR10 |
| DV P8, DV увімкнено, 1080p | `DVHE.ST` | `DolbyVision 1`, **UHD 0** | ❌ молоко |
| DV P8, DV увімкнено, 4K, Dolby Vision Vivid | `DVHE.ST` | `DolbyVision 1`, UHD 1 | ❌ помаранчеве `#602714` |
| DV P8, DV увімкнено, Dovi Bright | `DVHE.ST` | `DolbyVision 1` | ❌ фіолетове `#C62588` |

**Підтверджено:** ламається **обробка Dolby Vision**, незалежно від роздільності
(1080p і 4K однаково) і незалежно від режиму картинки.

**НЕ підтверджено (помилково висловлено раніше):** що HDR10-тонмапінг на проєкторі
правильний. Тест у VLC цього не доводить — VLC не вмикає DV, а грає базовий шар.
Окремого тесту «звичайний HDR10-файл» ще не було.

Усі попередні вимірювання «молока» зроблені в DV-активних станах, тому «молоко»
усе ще пов'язане з DV-шляхом — але це не виключає того, що частина проблеми
приходить саме з HDR10.

### 4.1 Практичний наслідок

Файл зроблено у профілі 8 (single-layer): базовий шар HDR10-сумісний, і
**на пристроях без DV грається як HDR** (так прямо написано в описі релізу).
Отже **правильний спосіб дивитися цей контент на цьому проєкторі — саме те,
що робить VLC зараз**. Це не компроміс, а штатний режим файлу.

Обхід «зняти Dolby Vision у Kodi» — не хак, а коректний вибір режиму.

### 4.2 Що лишається неполагодженим

Тільки власне обробка DV: переговори буфера між `DVHE.ST`-декодером і
поверхнею (`setPortMode ... -1010`, `BadPortIndex`). Точка правки — вендорний
код поза досяжним статично (див. §1.6).

## 5. РЕПЛІКАЦІЯ НА ДВОХ ПЛЕЄРАХ (2026-10-02) — висновок закритий

Користувач встановив другий плеєр з повноцінною підтримкою DV.
Результат: **DV вмикається, колір знову неправильний.**

| Плеєр | DV активний | Колір |
|---|---|---|
| Kodi | ✅ (`DVHE.ST`) | ❌ |
| Другий плеєр (Vimu) | ✅ | ❌ |
| VLC | ❌ (DV ігнорується) | ✅ |

**Висновок: поламка не на боці Kodi.** Гіпотеза «`DynamicANWBuffer` — режим Kodi,
в іншому плеєрі минеться» — **спростована**. `setPortMode ... -1010` був
симптомом, а не причиною.

**Обробка Dolby Vision на цьому проєкторі не працює коректно з будь-яким
плеєром.** Єдиний правильний режим перегляду DV P8-контенту — ігнорувати шар DV
і грати базовий шар HDR10 (саме так і описано в релізі: «на пристроях без DV
гратиме HDR»).

Перезавантаження не змінює суті: воно лише перемикає між двома DV-симптомами
(«молоко» після старту, помаранчеве/фіолетове після повторного входу).
